# Ответы заказчику по развёртыванию и эксплуатации Script Factory

Дата подготовки: 26 ноября 2026 года. Версия системы: **0.17.8**, коммит `184f8b0`.

Ответы относятся к реализации в локальном репозитории. Наличие функции в коде не означает, что она уже внедрена и испытана на всех УН заказчика. Основной механизм централизованных обновлений реализован; дополнительные требования и необходимые доработки указаны в соответствующих ответах.

## Централизованное развёртывание и обновление

### 1. Как работает обновление УН, которая выключена или на паузе?

Команда обновления сохраняется на центральном сервере. После включения или возобновления работы УН её агент связывается с центром и получает команду, если окно обновления ещё действует и раскатка разрешена.

Система самостоятельно не включает УН и не снимает паузу виртуальной машины через гипервизор. Для этого потребуется интеграция с инфраструктурой виртуализации.

### 2. Что происходит, если УН становится доступной после окончания периода выполнения задания? Не теряется ли задание автоматически?

Задание не удаляется автоматически. Выдача новых команд прекращается, раскатка приостанавливается с причиной `WINDOW_EXPIRED`. Оператору нужно изменить временное окно и продолжить раскатку.

Уже начатая установка может завершиться после окончания окна. Доработка для сохранения ожидающих заданий не требуется.

### 3. Можно ли вручную отменить ожидающее задание?

Да. Отмена раскатки отменяет все её операции, которые ещё находятся в очереди. Уже начавшаяся установка продолжает безопасное завершение.

Отдельной отмены одной ожидающей УН внутри раскатки в текущем API нет. Для выборочной отмены потребуется доработка.

### 4. Как система определяет, что обновление действительно завершилось успешно?

Проверяются:

- подпись пакета, размер и контрольная сумма;
- совпадение установленной версии с целевой и правильность `UN_ID`;
- работоспособность API, базы, файловой системы и браузера;
- выполнение контрольного JSON-сценария с записью и чтением временного артефакта;
- возврат API в рабочий режим после обслуживания.

Только после этого фиксируется `succeeded`. Контрольный сценарий проверяет техническую работоспособность исполнителя. Успешную отправку реального отчёта в СБИС он не подтверждает: для этого нужен отдельный приёмочный сценарий.

### 5. Где и как отображается текущая версия API и скрипта на каждой УН?

В центральной панели по каждой УН отображаются версия API, версия исходников агента, связь и готовность. Локально версия API доступна через `/health` и `/api/v2/health`.

Показанная в центре версия — последнее полученное сообщение агента. Для выключенной УН нужно учитывать время последнего контакта.

Единого учёта версий бизнес-скриптов по всему парку сейчас нет. Сценарий может передаваться вместе с заданием, поэтому его версия не обязательно является постоянным свойством УН. Для полного контроля потребуется реестр сценариев: идентификатор, версия, хеш и фиксация фактически выполненного сценария в задании и панели.

### 6. Как отображаются ошибки обновления и можно ли понять причину неудачного выполнения?

В панели доступны состояние операции, код ошибки, пояснение, причина ожидания и события центра. Карточка диагностики показывает пути к локальным журналам установки и отката.

Подробный PowerShell-протокол хранится на самой УН и автоматически в центр не загружается. Для просмотра полного журнала непосредственно из панели потребуется доработка сбора журналов.

### 7. Что происходит, если обновление прерывается или завершается ошибкой?

Поведение зависит от этапа:

- до установки операция может завершиться ошибкой или быть отложена;
- при неудачном запуске новой версии предусмотрен автоматический откат;
- после перезапуска агент читает сохранённый журнал и результат установщика;
- если результат невозможно достоверно установить, операция получает `recovery_required`.

При неизвестном результате система сохраняет обслуживание и требует проверки инженером. Ошибка обновления не считается доказательством успешного отката. Дальнейшая раскатка приостанавливается.

### 8. Как откатиться на предыдущую версию скрипта?

Для бизнес-сценария JSON нужно повторно передать предыдущую сохранённую версию. Уже выполненные действия на внешнем сайте и изменения файлов такой откат не отменяет. Для удобного выбора версий из панели нужен реестр сценариев.

Для кода API и исполнителя при неудачном обновлении используются резервная копия и автоматический откат. Произвольное понижение версии через обычную раскатку не поддерживается: агент требует, чтобы целевой релиз был новее установленного.

Без доработки системы можно восстановить нужный код из истории GitHub, присвоить ему номер релиза выше установленного, собрать и подписать новый пакет и распространить его обычной раскаткой. Например, прежний код можно выпустить как 0.17.9 поверх установленной 0.17.8. Фактически это возврат к прежнему коду, оформленный как новый релиз. Подробности и условия приведены в ответе 21.

### 9. Как система ведёт себя, если на УН в момент обновления выполняется задание?

Агент включает обслуживание: приём новых заданий блокируется, а уже принятые задания, повторы, callback и передачи артефактов должны завершиться.

По умолчанию ожидание ограничено 30 минутами и оставшимся окном обновления. При превышении срока установка откладывается; после трёх отложенных попыток операция завершается ошибкой и раскатка приостанавливается. Штатный процесс не должен прерывать рабочий сценарий ради обновления.

### 10. Можно ли ограничивать количество одновременно обновляемых УН?

Да. Есть общий лимит центра `FLEET_MAX_CONCURRENT` и размер партии конкретной раскатки `batch_size`. Также поддерживаются пилотные УН: остальные начинают обновляться после успешного завершения всех пилотов. Доработка не требуется.

### 11. Как добавляются новые УН и можно ли добавлять их группами или автоматически?

Одна УН регистрируется через панель. Массовая регистрация выполняется по JSON-инвентарю; предусмотрено преобразование существующего CSV. Можно назначать группы, общие профили и индивидуальные настройки.

Есть средства первоначальной установки через WinRM и Ansible. Сеть, административный доступ, Node.js, браузер, криптокомпоненты и пользователь worker должны быть подготовлены.

Автоматическое обнаружение новых машин и их подключение без подготовленного инвентаря не реализовано. Для этого потребуется доработка.

## Управление нагрузкой и выключение УН

### 12. Можно ли встроить модуль выключения УН в процесс обновления?

Модуль уже согласован с обновлением: режим обслуживания блокирует выключение, сон и гибернацию. После успешного завершения обслуживания снова действует сохранённая политика питания.

Если требуется обязательная последовательность «обновить → подтвердить результат → выключить», её нужно добавить как отдельный завершающий этап. Текущая фоновая политика может выключить свободную УН, но не является подтверждённой командой завершения раскатки.

### 13. Как проверяет модуль наличие активных пользователей и сессий?

Через Windows WTS перечисляются локальные и RDP-сеансы, включая отключённые. Проверяется время последнего ввода каждого пользователя, кроме настроенной исключаемой учётной записи. Исключение сопоставляется по SID.

При неизвестном состоянии сеанса или ошибке чтения выключение блокируется. Дополнительно проверяются очередь API, выполняющиеся обработчики, callback и передачи файлов.

Отсутствие ввода не означает завершение длительного расчёта в 1С или другой программе. Для защиты таких операций вне очереди API потребуется дополнительная блокировка, например продлеваемая самой 1С на время работы.

### 14. Можно ли массово изменить параметр, если сохранённая конфигурация имеет приоритет над .env?

Да. Централизованное применение профиля обновляет не только `.env`, но и соответствующие сохранённые настройки очереди и питания. Поддерживаются пилот, окно применения, ограничение параллельности и откат.

Для массовой настройки питания также есть отдельный PowerShell-инструмент. Менять файлы вручную на каждой УН не требуется.

Это относится к поддержанным параметрам. Перенос каталога данных, смена порта или пользователя worker требуют отдельного плана.

### 15. Можно ли отказаться от приоритета конфигурационного файла и постоянно брать значения из .env?

Можно, но это изменение действующей модели конфигурации.

Сейчас `.env` задаёт исходные значения, а изменения через API сохраняются и переживают перезапуск. Если читать только `.env`, потребуется либо отказаться от сохранённых изменений через API, либо научить API безопасно изменять сам `.env`.

Постоянное перечитывание `.env` требует правил проверки и согласованного применения: API и worker должны получить одинаковые значения, а часть настроек всё равно требует перезапуска.

Для массового управления текущий механизм уже подходит. Если нужен единственный источник настроек, необходимо отдельно спроектировать его, включая миграцию существующих переопределений.

## Выполнение скриптов

### 16. Почему одинаковый скрипт в разных запусках может давать разные результаты?

Результат зависит от исходных файлов, состояния сайта и авторизации, ЭЦП, браузерного профиля, сетевых задержек, настроек УН и действий предыдущих запусков.

Например, первый запуск может переместить XML в архив, а следующий уже не найдёт его в исходной папке. Повтор сценария не возвращает внешнюю систему и файлы в первоначальное состояние.

Для разбора конкретного случая нужны журналы двух запусков, входные параметры, версии и хеши сценариев. Для повышения воспроизводимости нужны проверки состояния, ожидания конкретных условий и защита от повторного выполнения бизнес-действий.

### 17. Все ли сетевые пути корректно обрабатываются при выполнении скриптов?

Поддержка UNC-путей предусмотрена, но гарантировать работу любого сетевого пути нельзя. Необходимо:

- включить общую папку в `FILESYSTEM_ALLOWED_ROOTS`;
- выдать права фактическому пользователю worker;
- обеспечить доступность ресурса из его сеанса;
- корректно записать путь в JSON;
- проверить шаги загрузки через интерфейс сайта.

Подключённая буква диска может отсутствовать в другом сеансе или у SYSTEM, поэтому предпочтителен UNC-путь.

В документации сценария СБИС отдельно указано ограничение перехода в файловом диалоге: для сетевого пути могут потребоваться дополнительные `upload_directory_steps`. Нужна проверка конкретных сценариев; универсальная совместимость пока не подтверждена.

### 18. Как повторно запускается неудачное задание?

Автоматические повторы задаются `retry_policy`: максимальное число попыток и пауза между ними. Повторяется весь сценарий с исходными параметрами. Уже выполненные внешние действия и изменения файлов не откатываются.

После окончательной ошибки сценарий можно отправить новым заданием. Перед повтором отправки отчётов необходимо сверить фактический результат предыдущего запуска, чтобы избежать дублей.

Повтор обновления УН — отдельный механизм: оператор создаёт новую попытку проблемной операции и продолжает раскатку.

### 19. Как обеспечивается совместимость скриптов с разными версиями API и старым Ассистентом?

Поддерживаются несколько форматов исполнения, включая совместимый `json-steps`. Для пакетов обновления проверяется минимальная версия API.

Отдельных доработок для совместимости со старым Ассистентом не выполнялось. При этом новая система не должна создавать препятствий его работе. Совместную работу следует проверить на фактической конфигурации заказчика, включая используемые порты, каталоги и доступ к общим ресурсам; это ожидание, а не подтверждение проведённых испытаний.

Полной автоматической проверки совместимости произвольного бизнес-сценария с версией API сейчас нет. Для гарантированной поддержки разных версий API нужны матрица совместимости и проверка необходимых возможностей до запуска. Необходимость адаптера для старого Ассистента можно определить только при обнаружении конкретных различий используемых контрактов.

## Архитектура и дальнейшая эксплуатация

### 20. Что произойдёт, если центральный сервер или его веб-интерфейс станет недоступен?

При недоступности только панели локальные API и worker продолжают работу. Если сам центральный сервис доступен, агенты продолжают обмен с ним.

При недоступности всего центра локальное выполнение заданий не требует его постоянного участия. Новые централизованные назначения и получение пакетов будут недоступны. Локальные журналы агента и неподтверждённые отчёты сохраняются.

Уже запущенная локальная установка может завершиться без центра, если необходимые файлы получены. После восстановления связи агент передаст результат. Конкретное продолжение зависит от этапа сбоя.

Автоматическое резервирование центра не предусмотрено. При требовании высокой доступности нужны отдельные инфраструктурные работы.

### 21. Как выполняется откат на предыдущую версию API?

При неудачном обновлении предусмотрен автоматический возврат из резервной копии с проверкой восстановленной версии.

Для отката уже успешно принятого релиза требуется контролируемая административная процедура: обслуживание, завершение работ, восстановление подходящей копии кода, зависимостей и настроек, проверка здоровья и сценария. Обычная раскатка более старого релиза блокируется агентом.

Есть вариант без доработки механизма отката: восстановить нужный код из истории GitHub и выпустить его под новым номером, который выше установленного. Например, если установлена 0.17.8, проверенный код предыдущего релиза можно оформить как 0.17.9. Нужно согласованно обновить метаданные версии, собрать и подписать пакет, опубликовать его в центре и выполнить обычную раскатку с пилотной УН. Проверка отсутствия даунгрейда при этом сохраняется: система получает формально более новый релиз.

Такой подход позволяет сэкономить на отдельной доработке отката, хотя сама доработка небольшая. Он требует подготовки нового пакета при каждом таком возврате. Для удобного массового отката кнопкой из панели потребуется отдельная доработка.

Перед возвратом необходимо проверить совместимость прежнего кода с текущими данными, конфигурацией и протоколом агента. Повышение номера версии само по себе такую совместимость не обеспечивает. Следует сохранить в описании нового релиза исходный Git-коммит, чтобы было понятно, какой код фактически установлен.

### 22. Как обеспечивается сохранность конфигурации и настроек при обновлении?

Штатное обновление сохраняет действующие настройки и данные, создаёт резервные копии кода, `.env`, задач запуска и при необходимости зависимостей. Обновление конфигурации дополнительно сохраняет затрагиваемые runtime-настройки.

Откат конфигурации восстанавливает соответствующие параметры, не подменяя всю рабочую базу поверх новых заданий и результатов.

Резервное копирование центральной БД, пакетов и ключей нужно настроить отдельно. Для восстановления зашифрованных секретов необходим соответствующий master key.

### 23. Какие действия должен выполнять инженер при выпуске новой версии? Нужны ли Git, сборка, веб-интерфейс и отдельные конфигурационные файлы?

При текущем процессе инженер:

1. Получает согласованный коммит проекта на компьютере выпуска.
2. Формирует подписанный пакет и публикует его в центре.
3. Выбирает в панели релиз, УН, пилотов, окно и параллельность.
4. Проверяет пилот, включая бизнес-сценарий.
5. Контролирует остальные УН и разбирает исключения.

Работа с Git и командами подготовки пакета сейчас нужна на компьютере выпуска. На каждой УН она не нужна. Править отдельные конфигурационные файлы при обычном выпуске не требуется; изменение настроек выполняется отдельным применением профиля.

Для процесса «инженер только выбирает готовый релиз в панели» потребуется автоматизировать сборку, подпись и публикацию через CI/CD.

### 24. Какие операции выполняются автоматически, а какие остаются ручными?

| Автоматически | Вручную или внешними средствами |
| --- | --- |
| Ожидание доступности агента в пределах окна | Включение УН и снятие паузы ВМ |
| Пилотная последовательность и лимиты параллельности | Выбор релиза, группы, окна и пилотов |
| Обслуживание и ожидание завершения работ | Подготовка инфраструктуры и первичный доступ |
| Получение и проверка пакета | Выпуск, подпись и публикация пакета текущими CLI |
| Резервирование, установка и технические проверки | Приёмка бизнес-сценария |
| Откат при предусмотренных сбоях | Разбор `recovery_required` |
| Передача состояний и результатов в центр | Продление истёкшего окна, повтор и продолжение |
| Применение поддержанных массовых настроек | Резервирование центра и хранение ключей |

## Доработки при включении дополнительных требований

Основной механизм централизованных обновлений уже реализован. Доработки потребуются, если в требования входят:

- включение и возобновление УН через гипервизор;
- отмена отдельной УН внутри раскатки;
- централизованный учёт версий бизнес-сценариев;
- просмотр полных локальных журналов из панели;
- обязательное выключение после подтверждённого обновления;
- защита длительных операций 1С вне очереди API;
- устранение конкретных несовместимостей со старым Ассистентом, если они будут выявлены при совместной проверке;
- массовый откат успешно установленного релиза отдельной командой из панели; возврат прежнего кода под новым номером релиза доступен без этой доработки;
- выпуск релизов без ручной работы инженера с Git и CLI.

Автоматическое обнаружение новых УН, высокая доступность центра и переход к единственному источнику конфигурации также требуют отдельных работ, если заказчик включает их в требования.

Перед промышленным внедрением нужен пилот на фактических Windows-УН заказчика. Наличие локальных проверок не подтверждает промышленную приёмку массового развёртывания и всех режимов выключения.
