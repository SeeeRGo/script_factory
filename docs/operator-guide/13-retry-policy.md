# Повторные попытки выполнения задания

С API 0.14.0 решение о повторах определяет отправитель через `parameters.retry_policy` (либо `retry_policy` в плоском запросе). Правило одинаково для `json-workflow`, нативного Recorder/Replay и совместимого старого `json-steps`. Исполнитель не классифицирует ошибки как разрешённые или запрещённые для повтора. `retryable` в ошибках выполнения больше не формируется и не учитывается, даже если старый скрипт/исполнитель его передал.

```json
{
  "parameters": {
    "retry_policy": {
      "max_attempts": 3,
      "backoff_ms": 1000
    }
  },
  "script": {
    "format": "json-workflow",
    "steps": [
      {
        "action": "fail",
        "title": "Проверить политику повторов",
        "params": {
          "error_code": "DEMO_ERROR",
          "message": "Контролируемая ошибка"
        }
      }
    ]
  }
}
```

Перед отправкой добавьте остальные обязательные параметры вашей интеграции, авторизацию и при необходимости uid. Вместо `script` можно передать весь JSON сценария строкой в `script_text`.

`max_attempts: 3` — максимум три исполнения целиком: первоначальное и два повторных. `max_attempts: 1` — без повторов. `backoff_ms` задаёт паузу перед следующим исполнением; эта пауза фиксированная. После успеха повторов нет.

Если поля не переданы, действуют значения `system/config.retry_policy`. При первом запуске API они берутся из `RETRY_MAX_ATTEMPTS` и `RETRY_BACKOFF_MS` в env; сохранённая конфигурация API имеет свой жизненный цикл. Для воспроизводимого поведения передавайте оба поля в каждом задании. Изменение настроек по умолчанию не меняет уже созданное задание.

## Что именно повторяется

Каждая ошибка исполнения — включая ошибку проверки, отсутствие файла, повторный импорт, ошибку авторизации, HTTP или тайм-аут отдельного шага — может запустить следующую попытку в пределах бюджета. Ошибка с произвольным кодом из `fail` или `assert` обрабатывается тем же способом. API не анализирует текст сообщения.

Повтор запускает **весь сценарий сначала** с исходными входными параметрами, а не только упавший шаг. Переменные предыдущего исполнения не переносятся. Изменения внешнего сайта и файлы, которые сценарий уже переместил/создал, не откатываются. Например, если первый запуск СБИС перенёс XML в error_dir, следующий запуск снова ищет файлы в root_dir и видит его фактическое текущее содержимое. Результат задания соответствует последней попытке; события предыдущих попыток остаются в журнале. Учёт отправленных отчётов и идемпотентность задаёт автор сценария.

При разрыве связи с worker повтор ждёт его готовности. Новый запуск не происходит параллельно старому: worker завершает/останавливает прежние исполнения перед повторным подключением. После рестарта API прерванная попытка считается использованной; при оставшемся бюджете задание снова ставится в очередь. Если бюджет исчерпан, ошибка `WORKER_EXECUTION_UNCERTAIN` завершает задание. Отменённые задания при восстановлении не возобновляются.

## Отмена, тайм-ауты и ошибки самого запроса

- Явная отмена останавливает задание и дальнейшие попытки.
- Тайм-аут отдельного шага допускает повтор всего сценария по политике. После исчерпания попыток возвращается `timeout`.
- Верхний `timeout_ms` ограничивает текущую попытку выполнения (и ожидание следующей попытки до её постановки в очередь). Истечение этого срока останавливает задание со статусом `timeout`. При запуске следующей попытки отсчёт начинается заново. Это не общий срок всех попыток вместе.
- Неверный HTTP-запрос, ошибка авторизации API или отклонённый до постановки в очередь JSON не являются попыткой исполнения задания. Их повторяет HTTP-клиент по своей логике.
- `callback.max_attempts` управляет только доставкой результата в 1С. Callback доставляется после окончательного результата задания; сбой callback не перезапускает сценарий.

## Контекст и артефакты

Во workflow доступны системные переменные:

| Переменная | Значение |
| --- | --- |
| `attempt` | Номер текущей попытки, начиная с 1. |
| `job_id` | Идентификатор задания. |
| `artifact_dir` | Фактический каталог артефактов текущей попытки. |
| `service_base_url` | Базовый адрес API из SERVICE_BASE_URL либо локальный адрес сервиса. |

`job_id`, `attempt`, `artifact_dir` и `service_base_url` устанавливает исполнитель. Они не меняют пользовательские настройки каталогов root_dir, loaded_dir или error_dir. Для первой попытки сохраняется каталог `<DATA_DIR>/artifacts/<job_id>`. Для следующих используется `<DATA_DIR>/artifacts/<job_id>/attempt-2`, `attempt-3` и т. д. Поэтому одинаковые имена снимков/артефактов разных попыток не конфликтуют. Публичные API-ссылки на файлы по-прежнему выдаются в `result.artifacts`; не собирайте внутренние пути вручную.

Пример успеха со второй попытки — [demo/retry.json](../../demo/retry.json). Сценарий проверяет `attempt`, создаёт ошибку при первом запуске и сохраняет результат при втором. Никаких специальных имитаторов `auth_ecp` в этом демо нет.

## Ожидание готовности API — отдельный механизм

В `/health`, статусе worker и HTTP 503 при приёме задания сохранено поле `retryable`: оно сообщает 1С, можно ли ещё ждать входа пользователя/запуска worker. Этот признак относится к доступности сервиса **до исполнения**, а не к ошибке сценария. Он не ограничивает `retry_policy` принятого задания. См. [запуск API и worker](../project-guide/12-api-worker-startup.md).
