# Ответы по интеграции 1С с УН

Документ фиксирует ответы и принятые изменения по состоянию на 4 сентября 2026 года.

## 1. Как определить готовность УН

Перед постановкой задания 1С вызывает:

```http
GET http://TEST_UN_HOST:33001/health
```

Задание можно отправлять, если одновременно выполнены условия:

- получен HTTP 200;
- `status` равен `ok`;
- `ready` равен `true`;
- `service` равен `script-factory`;
- `un_id` совпадает с идентификатором ожидаемой УН;
- проверки `checks.database`, `checks.filesystem` и `checks.browser` имеют `status: ok`.

`queue.available_slots = 0` не запрещает постановку. УН примет задание в очередь.
`queue.status` имеет значения `idle`, `processing` или `busy` и отражает только
текущую загрузку очереди.

Проверка браузера подтверждает наличие доступного исполняемого файла Chromium или
Яндекс Браузера. Ошибки конкретного сайта, профиля или запуска сценария остаются
ошибками выполнения задания.

Если сервис уже отвечает, но не готов, возвращается HTTP 503 и тело вида:

```json
{
  "status": "error",
  "ready": false,
  "error": {
    "code": "BROWSER_UNAVAILABLE",
    "message": "Не найден исполняемый файл Chromium или Яндекс Браузера"
  },
  "checks": {
    "database": { "status": "ok" },
    "filesystem": { "status": "ok" },
    "browser": { "status": "error", "message": "..." }
  }
}
```

Пока процесс ещё не открыл порт, 1С получит ошибку соединения или тайм-аут, поэтому
проверку нужно повторять каждые 1–2 секунды с общим пределом 30–60 секунд. Несовпадение
`un_id` является ошибкой конфигурации и не должно повторяться бесконечно.

## 2. Текст ошибок

Ошибки HTTP API возвращаются в `error.code`, `error.message` и при необходимости
`error.details`. Ошибка завершённого задания находится в `job.error`. Если ошибка
возникла на конкретном шаге, дополнительно доступны его номер `step_index` и действие
`action`; для общих ошибок задания эти поля могут отсутствовать.

## 3. `job_id` и `uid`

- При интеграции с 1С `uid` должна создавать 1С: он идентифицирует заявку на выполнение
  и служит ключом идемпотентности. Если не переданы ни `uid`, ни `Idempotency-Key`, УН
  сгенерирует `uid` автоматически, но такой вариант не подходит для безопасного повтора
  запроса со стороны 1С.
- `job_id` создаётся УН и является внутренним идентификатором запуска, журналов,
  callback и каталога артефактов.

Использовать внешний `uid` как внутренний `job_id` не требуется. Чтобы 1С могла
работать по своему идентификатору без хранения дополнительного индекса, добавлен метод:

```http
GET /api/v2/jobs/by-uid/{uid}
```

`uid` должен быть уникален для заявки, а не только для объекта 1С. Для повторной
операции над одним объектом формируется новый `uid`, например
`<uid объекта>:<операция>:<версия>`.

## 4. Проверка дубликатов

При повторном POST проверяются все задания, хранящиеся в SQLite данной УН: ожидающие,
выполняющиеся и завершённые. Автоматического удаления истории сейчас нет.

- одинаковый `uid` и одинаковое содержимое возвращают исходное задание, HTTP 200 и
  `idempotent: true`;
- одинаковый `uid`, но отличающиеся параметры или сценарий возвращают HTTP 409 и
  `IDEMPOTENCY_CONFLICT`;
- если одновременно переданы `uid` и `Idempotency-Key`, они должны совпадать.

Удаление или замена `data/state.sqlite`, а также обращение к другой УН обнуляет область
проверки дубликатов.

## 5. Callback

Механизм `CALLBACK_ALLOWED_ORIGINS` оставлен без изменений. В задании передаётся полный
абсолютный `callback.url`, а переменная окружения при заполнении ограничивает допустимые
origin. Пустое значение разрешает любой HTTP/HTTPS callback и менее безопасно из-за
риска SSRF, ошибочной отправки результата и утечки callback-токена.

## 6. Развёртывание рабочих УН

Ansible можно использовать, и он принят основным способом синхронной раскатки на группу
Windows-УН. Управление выполняется с Linux-контроллера по WinRM. Сам worker запускается
нативно через Windows Scheduled Task, а не в Docker: так видимый Яндекс Браузер работает
в интерактивной пользовательской сессии. Docker остаётся вариантом для headless/server
и демонстрационного noVNC-окружения.

В проект добавлены [`ansible/deploy-windows.yml`](../ansible/deploy-windows.yml) и
подробная [`инструкция по эксплуатации`](../ansible/README.md). Схема размещения:

| Данные | Каталог на УН |
|---|---|
| неизменяемый код релиза | `C:\ProgramData\ScriptFactory\releases\<release-id>` |
| конфигурация релиза | `C:\ProgramData\ScriptFactory\shared\configs\<release-id>.env` |
| SQLite | `C:\ProgramData\ScriptFactory\shared\data` |
| входящие, исходящие и архивные файлы | `C:\ProgramData\ScriptFactory\shared\work` |

Playbook выполняет следующий цикл:

1. На контроллере собирает ZIP только из отслеживаемых файлов точного Git commit/tag.
2. Проверяет Node.js 24+, Яндекс Браузер, обязательные переменные и Windows preflight.
3. Копирует новый релиз, устанавливает production-зависимости и создаёт защищённый
   версионный `.env`. Секреты берутся из Ansible Vault; доступ к `.env` получают только
   SYSTEM, локальные администраторы и worker-пользователь.
4. Останавливает текущую Scheduled Task только перед переключением и направляет её на
   новый релиз.
5. Принимает релиз только после HTTP 200 от `/health`, `ready=true`, совпадения `un_id`
   и успешных проверок базы, файловой системы и браузера.
6. Если health-gate не пройден, возвращает предыдущие код и `.env`, запускает прежнюю
   Scheduled Task и повторно проверяет её `/health`.

По умолчанию УН обновляются партиями по 25%. Сначала следует выполнить `--limit` для
одной пилотной УН, затем раскатать тот же commit/tag на остальные машины. Значение
`script_factory_serial=100%` запускает максимально синхронное обновление всей выбранной
группы, но увеличивает область отказа. Один и тот же `release-id` повторно не
разворачивается.

Предварительно на каждой УН должны быть установлены Node.js 24+ и Яндекс Браузер,
настроен WinRM HTTPS/Kerberos, а deployment-пользователь должен иметь административные
права. Worker-пользователю playbook выдаёт `SeBatchLogonRight`, но для headed-режима он
должен быть уже залогинен: Ansible не создаёт интерактивную Windows-сессию. Доменная GPO
может переопределить это право.

`CALLBACK_ALLOWED_ORIGINS` при переходе на Ansible не меняется и передаётся через
`script_factory_callback_allowed_origins`. Перед промышленной раскаткой остаётся
обязательным пилот на реальных УН с проверкой WinRM, сертификатов/Kerberos, доменных
политик, ЭЦП/СБИС и поведения RDP. Базовый механизм реализован, но такой пилот в текущем
окружении проекта не выполнялся.

## 7. Разделённый формат постановки задания

Рекомендуемый новый формат отделяет параметры задания от текста сценария:

```json
{
  "parameters": {
    "uid": "1c-job-000042",
    "priority": 8,
    "timeout_ms": 180000,
    "retry_policy": {
      "max_attempts": 2,
      "backoff_ms": 500
    },
    "context": {
      "document_id": "42"
    },
    "callback": {
      "url": "http://1c-test.local:8080/script-factory/result"
    },
    "log_level": "info"
  },
  "script_text": "{\"title\":\"Сценарий\",\"steps\":[{\"action\":\"noop\"}]}"
}
```

`script_text` должен содержать сериализованный JSON-объект сценария. API также принимает
`parameters` вместе с `script`-объектом. Старый плоский формат, в котором параметры и
`script` находятся на верхнем уровне, сохранён для обратной совместимости. Смешивать
поля параметров верхнего уровня с объектом `parameters` нельзя; одновременно передавать
`script` и `script_text` также нельзя.

## 8. Полный цикл `download-save-open`

В `demo/download-save-open.json` добавлены `uid`, `callback` и `log_level`. Перед
отправкой из 1С нужно заменить `REPLACE_WITH_UNIQUE_1C_UID` и тестовый callback URL.

Цикл работы:

1. 1С отправляет POST и получает HTTP 201 с `job_id`.
2. УН скачивает, сохраняет, проверяет и открывает файлы.
3. При переходе в финальный статус УН отправляет callback с объектом задания, который
   всегда содержит поля `job.status`, `job.result` и `job.error`. При успехе `job.error`
   равен `null`; при ошибке заполнен `job.error`, а `job.result` может содержать частичный
   результат и созданные до ошибки артефакты.
4. 1С сохраняет событие идемпотентно и отвечает любым HTTP 2xx.
5. При необходимости 1С скачивает файл с API-авторизацией:

```http
GET /api/v2/jobs/{job_id}/artifacts/{artifact_id}
X-API-Key: <API_KEY>
```

Готовый относительный адрес находится в `result.artifacts[].api_url`.

При статусах `failed` и `validation_failed` JSON Steps-сценария в `result` сохраняются
частичный контекст и уже созданные артефакты, поэтому они также попадают в callback.
Для статусов `timeout` и `cancelled` частичный результат сейчас не формируется.

## 9. Диагностический `download-save-open2`

Файл `demo/download-save-open2.json` выполняет загрузку, чтение и открытие документа,
после чего предсказуемо завершается ошибкой `VALIDATION_ERROR`. Для него установлен
`log_level: debug` и `max_attempts: 1`.

Запуск локально:

```bash
npm run demo:file:error
```

Для реального callback при запуске через demo-runner задаётся:

```bash
DEMO_CALLBACK_URL=http://1c-test.local:8080/script-factory/result npm run demo:file:error
```

Demo-runner ждёт финального статуса задания, но не ожидает перехода
`callback_delivery` в `delivered`. После завершения runner сервис продолжает доставку
callback самостоятельно. Состояние доставки проверяется отдельным запросом
`GET /api/v2/jobs/{job_id}` или в callback-получателе 1С.

Допустимые уровни — `debug`, `info`, `warn`, `error`; по умолчанию используется
`info`. Журнал можно дополнительно фильтровать:

```http
GET /api/v2/jobs/{job_id}/logs?min_level=warn
```
