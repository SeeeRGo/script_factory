# Ответы по интеграции 1С с УН

Документ фиксирует ответы и принятые изменения по состоянию на 7 сентября 2026 года.
Дополнение от 18 сентября 2026 года по вопросам «Демо 4 часть 2» — в разделе 10.

## 1. Как определить готовность УН

Перед постановкой задания 1С вызывает:

```http
GET http://TEST_UN_HOST:33001/health
```

Задание можно отправлять, если одновременно выполнены условия:

- получен HTTP 200;
- `status` равен `ok`;
- `ready` равен `true`;
- `service` равен `script-factory`;
- `version` и `release_date` соответствуют ожидаемому релизу;
- `un_id` совпадает с идентификатором ожидаемой УН;
- проверки `checks.database`, `checks.filesystem` и `checks.browser` имеют `status: ok`.

`queue.available_slots = 0` не запрещает постановку. УН примет задание в очередь.
`queue.status` имеет значения `idle`, `processing` или `busy` и отражает только
текущую загрузку очереди.

Проверка браузера подтверждает наличие доступного исполняемого файла Chromium или
Яндекс Браузера. Ошибки конкретного сайта, профиля или запуска сценария остаются
ошибками выполнения задания.

Если сервис уже отвечает, но не готов, возвращается HTTP 503 и тело вида:

```json
{
  "status": "error",
  "ready": false,
  "service": "script-factory",
  "version": "0.5.0",
  "release_date": "07.09.2026",
  "un_id": "un-test-windows-01",
  "error": {
    "code": "BROWSER_UNAVAILABLE",
    "message": "Не найден исполняемый файл Chromium или Яндекс Браузера"
  },
  "checks": {
    "database": { "status": "ok" },
    "filesystem": { "status": "ok" },
    "browser": { "status": "error", "message": "..." }
  }
}
```

Пока процесс ещё не открыл порт, 1С получит ошибку соединения или тайм-аут, поэтому
проверку нужно повторять каждые 1–2 секунды с общим пределом 30–60 секунд. Несовпадение
`un_id` является ошибкой конфигурации и не должно повторяться бесконечно.

## 2. Текст ошибок

Ошибки HTTP API возвращаются в `error.code`, `error.message` и при необходимости
`error.details`. Ошибка завершённого задания находится в `job.error`. Если ошибка
возникла на конкретном шаге, дополнительно доступны его номер `step_index` и действие
`action`; для общих ошибок задания эти поля могут отсутствовать.

## 3. `job_id` и `uid`

- При интеграции с 1С `uid` должна создавать 1С: он идентифицирует заявку на выполнение
  и служит ключом идемпотентности. Если не переданы ни `uid`, ни `Idempotency-Key`, УН
  сгенерирует `uid` автоматически, но такой вариант не подходит для безопасного повтора
  запроса со стороны 1С.
- `job_id` создаётся УН и является внутренним идентификатором запуска, журналов,
  callback и каталога артефактов.

Использовать внешний `uid` как внутренний `job_id` не требуется. Чтобы 1С могла
работать по своему идентификатору без хранения дополнительного индекса, добавлен метод:

```http
GET /api/v2/jobs/by-uid/{uid}
```

`uid` должен быть уникален для заявки, а не только для объекта 1С. Для повторной
операции над одним объектом формируется новый `uid`, например
`<uid объекта>:<операция>:<версия>`.

## 4. Проверка дубликатов

При повторном POST проверяются все задания, хранящиеся в SQLite данной УН: ожидающие,
выполняющиеся и завершённые. Автоматического удаления истории сейчас нет.

- одинаковый `uid` и одинаковое содержимое возвращают исходное задание, HTTP 200 и
  `idempotent: true`;
- одинаковый `uid`, но отличающиеся параметры или сценарий возвращают HTTP 409 и
  `IDEMPOTENCY_CONFLICT`;
- если одновременно переданы `uid` и `Idempotency-Key`, они должны совпадать.

Удаление или замена `data/state.sqlite`, а также обращение к другой УН обнуляет область
проверки дубликатов.

## 5. Callback

Механизм `CALLBACK_ALLOWED_ORIGINS` оставлен без изменений. В задании передаётся полный
абсолютный `callback.url`, а переменная окружения при заполнении ограничивает допустимые
origin. Пустое значение разрешает любой HTTP/HTTPS callback и менее безопасно из-за
риска SSRF, ошибочной отправки результата и утечки callback-токена.

## 6. Развёртывание рабочих УН

Ansible можно использовать, и он принят основным способом синхронной раскатки на группу
Windows-УН. Управление выполняется с Linux-контроллера по WinRM. Сам worker запускается
нативно через Windows Scheduled Task, а не в Docker: так видимый Яндекс Браузер работает
в интерактивной пользовательской сессии. Docker остаётся вариантом для headless/server
и демонстрационного noVNC-окружения.

В проект добавлены [`ansible/deploy-windows.yml`](../ansible/deploy-windows.yml) и
подробная [`инструкция по эксплуатации`](../ansible/README.md). Для оператора также
подготовлена простая [`пошаговая инструкция обновления УН`](update-un-step-by-step.md).
Для единичной УН доступен отдельный вариант
[`ручного обновления без Ansible`](update-un-manual-step-by-step.md).
Схема размещения:

| Данные | Каталог на УН |
|---|---|
| неизменяемый код релиза | `C:\ProgramData\ScriptFactory\releases\<release-id>` |
| конфигурация релиза | `C:\ProgramData\ScriptFactory\shared\configs\<release-id>.env` |
| SQLite | `C:\ProgramData\ScriptFactory\shared\data` |
| входящие, исходящие и архивные файлы | `C:\ProgramData\ScriptFactory\shared\work` |

Playbook выполняет следующий цикл:

1. На контроллере собирает ZIP только из отслеживаемых файлов точного Git commit/tag.
2. Проверяет Node.js 24+, Яндекс Браузер, обязательные переменные и Windows preflight.
3. Копирует новый релиз, устанавливает production-зависимости и создаёт защищённый
   версионный `.env`. Секреты берутся из Ansible Vault; доступ к `.env` получают только
   SYSTEM, локальные администраторы и worker-пользователь.
4. Проверяет, что `queue.running` и `queue.queued` равны нулю. Если задания ещё есть,
   переключение не выполняется. На время обновления отправку новых заданий из 1С на
   выбранные УН нужно приостановить.
5. Останавливает текущую Scheduled Task только перед переключением и направляет её на
   новый релиз.
6. Принимает релиз только после HTTP 200 от `/health`, `ready=true`, совпадения `un_id`
   и успешных проверок базы, файловой системы и браузера.
7. Если health-gate не пройден, возвращает предыдущие код и `.env`, запускает прежнюю
   Scheduled Task и повторно проверяет её `/health`.

По умолчанию УН обновляются партиями по 25%. Сначала следует выполнить `--limit` для
одной пилотной УН, затем раскатать тот же commit/tag на остальные машины. Значение
`script_factory_serial=100%` запускает максимально синхронное обновление всей выбранной
группы, но увеличивает область отказа. Один и тот же `release-id` повторно не
разворачивается.

Предварительно на каждой УН должны быть установлены Node.js 24+ и Яндекс Браузер,
настроен WinRM HTTPS/Kerberos, а deployment-пользователь должен иметь административные
права. Worker-пользователю playbook выдаёт `SeBatchLogonRight`, но для headed-режима он
должен быть уже залогинен: Ansible не создаёт интерактивную Windows-сессию. Доменная GPO
может переопределить это право.

`CALLBACK_ALLOWED_ORIGINS` при переходе на Ansible не меняется и передаётся через
`script_factory_callback_allowed_origins`. Перед промышленной раскаткой остаётся
обязательным пилот на реальных УН с проверкой WinRM, сертификатов/Kerberos, доменных
политик, ЭЦП/СБИС и поведения RDP. Базовый механизм реализован, но такой пилот в текущем
окружении проекта не выполнялся.

## 7. Разделённый формат постановки задания

Рекомендуемый новый формат отделяет параметры задания от текста сценария:

```json
{
  "parameters": {
    "uid": "1c-job-000042",
    "priority": 8,
    "timeout_ms": 180000,
    "retry_policy": {
      "max_attempts": 2,
      "backoff_ms": 500
    },
    "context": {
      "document_id": "42"
    },
    "callback": {
      "url": "http://1c-test.local:8080/script-factory/result"
    },
    "log_level": "info"
  },
  "script_text": "{\"title\":\"Сценарий\",\"steps\":[{\"action\":\"noop\"}]}"
}
```

`script_text` должен содержать сериализованный JSON-объект сценария. API также принимает
`parameters` вместе с `script`-объектом. Старый плоский формат, в котором параметры и
`script` находятся на верхнем уровне, сохранён для обратной совместимости. Смешивать
поля параметров верхнего уровня с объектом `parameters` нельзя; одновременно передавать
`script` и `script_text` также нельзя.

## 8. Полный цикл `download-save-open`

В `demo/download-save-open.json` добавлены `uid`, `callback` и `log_level`. Перед
отправкой из 1С нужно заменить `REPLACE_WITH_UNIQUE_1C_UID` и тестовый callback URL.

Цикл работы:

1. 1С отправляет POST и получает HTTP 201 с `job_id`.
2. УН скачивает, сохраняет, проверяет и открывает файлы.
3. При переходе в финальный статус УН отправляет callback с объектом задания, который
   всегда содержит поля `job.status`, `job.result` и `job.error`. При успехе `job.error`
   равен `null`; при ошибке заполнен `job.error`, а `job.result` может содержать частичный
   результат и созданные до ошибки артефакты.
4. 1С сохраняет событие идемпотентно и отвечает любым HTTP 2xx.
5. При необходимости 1С скачивает файл с API-авторизацией:

```http
GET /api/v2/jobs/{job_id}/artifacts/{artifact_id}
X-API-Key: <API_KEY>
```

Готовый относительный адрес находится в `result.artifacts[].api_url`.

При статусах `failed` и `validation_failed` JSON Steps-сценария в `result` сохраняются
частичный контекст и уже созданные артефакты, поэтому они также попадают в callback.
Для статусов `timeout` и `cancelled` частичный результат сейчас не формируется.

## 9. Диагностический `download-save-open2`

Файл `demo/download-save-open2.json` выполняет загрузку, чтение и открытие документа,
после чего предсказуемо завершается ошибкой `VALIDATION_ERROR`. Для него установлен
`log_level: debug` и `max_attempts: 1`.

Запуск локально:

```bash
npm run demo:file:error
```

Для реального callback при запуске через demo-runner задаётся:

```bash
DEMO_CALLBACK_URL=http://1c-test.local:8080/script-factory/result npm run demo:file:error
```

Demo-runner ждёт финального статуса задания, но не ожидает перехода
`callback_delivery` в `delivered`. После завершения runner сервис продолжает доставку
callback самостоятельно. Состояние доставки проверяется отдельным запросом
`GET /api/v2/jobs/{job_id}` или в callback-получателе 1С.

УН сохраняет HTTP-статус, Content-Type и тело ответа каждой попытки callback в
`callback_delivery.response_history`. Поля `last_http_status` и `last_response_body`
содержат последний ответ. Тело одной попытки ограничено 16 КиБ, а флаг
`body_truncated` показывает, было ли оно обрезано.

Для ручного воспроизведения ответов `401` и `402` можно импортировать в Postman файл
`docs/postman/callback-402.postman_collection.json`. После импорта в переменной
коллекции `validCallbackToken` нужно указать тот же ключ, что и в
`CALLBACK_AUTH_TOKEN` на УН.

Допустимые уровни — `debug`, `info`, `warn`, `error`; по умолчанию используется
`info`. Журнал можно дополнительно фильтровать:

```http
GET /api/v2/jobs/{job_id}/logs?min_level=warn
```

## 10. Ответы по вопросам «Демо 4 часть 2»

### 10.1 Проверка внешнего IP УН — отдельный метод

Проверка соответствия IP вынесена из health в отдельный метод, чтобы 1С выполняла
проверку один раз и сразу ставила задания:

```http
GET /api/v2/system/ip-check
X-API-Key: <API_KEY>
```

Метод при каждом вызове читает файл `C:\_external ip monitor\settings.ini` с УН,
берёт из секции `[main]` ключ `ip_adress`, определяет внешний адрес через сервис
ipify и сравнивает их. В ответе возвращается только статус проверки, значения IP
не передаются:

- HTTP 200 и `{"status":"success"}` — адрес совпал;
- HTTP 503 и `{"error":{"code":"...","message":"..."}}` — проверка не пройдена.

Коды ошибок: `IP_SETTINGS_READ_FAILED` (файл не прочитан), `IP_SETTINGS_INVALID`
(нет ключа `ip_adress` или адрес некорректен), `IP_LOOKUP_FAILED` (ipify недоступен),
`IP_LOOKUP_INVALID` (сервис вернул не IP), `IP_MISMATCH` (адрес не совпал) и
`IP_CHECK_TIMEOUT`. Health-проверки `/health` и `/api/v2/health` продолжают отвечать
независимо от проверки IP, ipify в них не вызывается.

### 10.2 Различие текстов логов при разных log_level

Тексты журнала при разных уровнях совпадают не полностью, но совпадение части записей
ожидаемо: уровень фильтрует записи до записи в журнал. Значения по умолчанию:

- `debug` и `info` содержат одинаковые служебные записи запуска и завершения шагов;
  при `debug` дополнительно появляются записи подготовки сценария и деталей;
- `warn` — только предупреждения (отмена задания, повторы после сбоя);
- `error` — только ошибки шагов и задания.

Если в задании не происходит предупреждений и ошибок, журналы `warn` и `error`
будут пустыми и потому одинаковыми, а журналы `debug` и `info` будут отличаться
только в случаях, когда код создаёт debug-записи. Одинаковый вид текста при
`debug` и `info` для конкретного сценария корректен: различие проявляется только
на сценариях, создающих debug-события.

### 10.3 Логи при `min_level=warn` для `cancelled` и `timeout`

Для обоих статусов фильтр возвращает записи: отмена — `warn` («Пользователь запросил
отмену задания», «Задание отменено»), тайм-аут — `error` («Превышен тайм-аут задания»)
с сообщением кода `TIMEOUT_ERROR`. Метод отвечает HTTP 200 и телом
`{job_id, log_level, logs}`; отличного от 200 кода, кроме перечисленных ниже, не бывает.

При коде состояния, отличном от 200, метод возвращает текстовое описание в
`error.code` и `error.message` (например, `JOB_NOT_FOUND` при неизвестном
`job_id`, `INVALID_LOG_LEVEL` при некорректном `min_level`). Это же правило действует
для скачивания артефактов: `ARTIFACT_NOT_FOUND` с текстовым описанием при 404 и
`UNAUTHORIZED` при отсутствии ключа.

### 10.4 `/api/v2/system/resources` — версии и уникальные имена полей

Метод вызывается раз в день и вручную; в него добавлены:

- `api_version` — версия API на УН, сейчас `v2`;
- `service_version` и `release_date` — версия и дата релиза сервиса из `package.json`;
- `yandex_browser_version` — версия Яндекс Браузера, определяемая на Windows через
  реестр (`Software\\Yandex\\YandexBrowser\\BLBeacon`, `version`), а на других платформах
  запросом версии бинарника; если определить не удалось, возвращается `null`, а не
  версия Chromium.

Все вложенные поля получили уникальные имена с префиксом структуры: `cpu.cpu_logical_cores`,
`memory.memory_total_bytes`, `disk.disk_total_bytes`, `memory_usage.memory_usage_rss`,
`queue.queue_running`, `browser_replay.browser_replay_available` и так далее. Повторяющихся
имён leaf-полей внутри разных структур больше нет.

### 10.5 Авторизация 1С при возврате результата — заголовки

Пользователь из публикации базы больше не используется. Авторизация передачи результата
настраивается на УН переменными окружения и передаётся в заголовках callback:

- `CALLBACK_AUTH_TOKEN` — отправляет заголовок `Authorization: Bearer <token>`;
- `CALLBACK_AUTH_USERNAME` и `CALLBACK_AUTH_PASSWORD` — отправляет `Authorization: Basic <base64>`;
- `CALLBACK_ALLOWED_ORIGINS` обязателен при включённой авторизации; HTTPS обязателен,
  кроме literal `127.0.0.1` и `[::1]`.

Логин и пароль не указываются в задании, сценарии, URL и `parameters`: неизвестные поля
`callback` отклоняются с HTTP 400. УН скрывает настроенные секреты из журналов и
сохраняемых ответов callback. Это соответствует требованию «передавать данные в
заголовках к методу» — 1С на своей стороне принимает заголовок `Authorization` при
приёме callback.

### 10.6 Параметры задания: верхний уровень или context

«Системные» параметры (`uid`, `priority`, `timeout_ms`, `retry_policy`, `log_level`,
`callback`) передаются на верхнем уровне структуры `parameters`. Параметры, наличие
которых зависит от конкретного сценария, передаются в `parameters.context`: они
попадают в контекст выполнения и подставляются в шаги по шаблонам `{{имя}}`.
Смешивать поля верхнего уровня с объектом `parameters` нельзя.

### 10.7 Новая структура `job.result`

Структура `job.result` изменена и содержит только два вида полей:

```json
{
  "artifacts": [
    "/api/v2/jobs/job_…/artifacts/step_1_1",
    "/api/v2/jobs/job_…/artifacts/step_2_1"
  ],
  "Rezult_1": { "Поле1": "…", "Поле2": "…" },
  "Rezult_2": { "Поле3": "…" }
}
```

Логика формирования:

- `artifacts` — массив путей всех сохранённых файлов без привязки к `Rezult_N`;
  путь готов для скачивания с API-авторизацией; если сценарий не скачивает файлы,
  массив пустой;
- `Rezult_N` — произвольные объекты результата, сценарий кладёт их в `context`
  с ключами `Rezult_1`, `Rezult_2`, …; состав полей внутри зависит от сценария;
- других полей в `job.result` нет: идентификаторы задания, `status`, `error`,
  контекст выполнения и диагностические данные остаются в соседних полях
  `job` (`job_id`, `uid`, `un_id`, `execution.context` и так далее).

Такая логика выстроена без потери универсальности API: сериализация результата
едина для JSON Steps и Chrome Recorder, для опроса статуса и callback, а набор
`Rezult_N` определяется только сценарием.

### 10.8 Файлы и логи

Логи задания хранятся в журнале задания (SQLite) и не записываются в каталог
скачанных файлов `DATA_DIR/artifacts/<job_id>`. Скачивание журнала через
`/jobs/{job_id}/logs` не смешивается с артефактами.

Если на УН нужно только скачать файл без передачи в 1С, это логика сценария:
шаг `download_files` без последующих шагов сохранит файл в каталог артефактов
задания; API не меняется, параметр «передавать/не передавать» в API отсутствует.

### 10.9 Очередь и таймауты

Ограничения на количество заданий в очереди нет: очередь приоритетная, безлимитная,
а `queue.available_slots = 0` лишь показывает занятость выполнения. Если потребуется
адмиссионный лимит, его нужно добавлять отдельно.

`timeout_ms` — общее ограничение времени выполнения задания. Тайм-аут шага задаётся
в JSON сценария и с `timeout_ms` не связан; поведение при превышении шагом своего
таймаута — задание завершается ошибкой `TIMEOUT_ERROR` со статусом `timeout`.
Параметр не бесполезен: он ограничивает сценарий целиком, включая паузы между шагами
и суммарное время, и срабатывает раньше, чем отдельные таймауты шагов, если общий
бюджет исчерпан первым. Рекомендация: задавать `timeout_ms` больше суммы таймаутов
шагов и пауз.
