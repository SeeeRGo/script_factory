# Демо логики приоритетной очереди

## Что подтверждают кейсы

Оба кейса используют только JSON Steps и не обращаются к браузеру, файлам или внешним
системам. Runner устанавливает `max_parallel_jobs = 1`, создаёт задания через обычный
`POST /api/v2/jobs`, наблюдает фактические статусы и сверяет результат с ожиданиями из
того же JSON.

Правило приоритета: **чем меньше число, тем выше приоритет**. Очередь невытесняющая:
появление P10 не отменяет и не приостанавливает уже выполняющийся P50. Приоритет влияет
только на выбор следующего задания после освобождения исполнительного слота.

Перед показом очередь должна быть пустой. Если в ней уже есть активные или ожидающие
задания, runner остановится, чтобы результат встречи оставался воспроизводимым.

## Ситуация 1 — два задания ожидают, первым падает высокий приоритет

JSON: [`demo/queue-case-priority-error.json`](../demo/queue-case-priority-error.json).

Целевые задания:

| Alias | Приоритет | Попытки | Ожидаемый итог |
|---|---:|---:|---|
| `high` | P10 | 2 | `failed / PLUGIN_NOT_RUNNING` |
| `low` | P50 | 1 | `success` |

Короткий технический job `gate` занимает единственный слот на три секунды. В это время
P50 и P10 одновременно появляются в колонке **«В очереди»**. После завершения `gate`
планировщик выбирает P10, хотя P50 был создан раньше. P10 получает retryable ошибку
`PLUGIN_NOT_RUNNING`, проходит `running → retrying → running`, повторяет JSON со второй
попытки и только затем окончательно падает. Благодаря P10 он остаётся первым и при
повторной постановке в очередь. После него запускается P50 и успешно завершается.

Запуск:

```bash
npm run demo:queue:priority-error
```

Что проговорить за 2–3 минуты:

1. На экране одновременно два ожидающих задания с P10 и P50.
2. Меньшее значение приоритета означает более срочную работу.
3. После освобождения слота P10 перемещается в «Выполняются» первым.
4. Первая ошибка переводит P10 в `retrying`, после backoff начинается попытка 2/2.
5. Вторая ошибка освобождает слот, P50 начинает выполняться и завершается успешно.

## Ситуация 2 — P10 приходит во время выполнения P50

JSON: [`demo/queue-case-running-low.json`](../demo/queue-case-running-low.json).

Целевые задания:

| Alias | Приоритет | Момент подачи | Попытки | Ожидаемый итог |
|---|---:|---|---:|---|
| `low` | P50 | сразу | 2 | `failed / PLUGIN_NOT_RUNNING` |
| `high` | P10 | через 800 мс после старта попытки 2/2 P50 | 1 | `success` |

P50 выполняет первую попытку, получает retryable ошибку и после backoff запускается
снова. Через 800 мс после начала попытки 2/2 поступает P10. P10 остаётся в очереди:
планировщик не прерывает активный job. P50 повторяет наглядные шаги и окончательно падает
по собственной причине `PLUGIN_NOT_RUNNING`. Только после его завершения P10 занимает
слот и успешно проходит все шаги.

Запуск:

```bash
npm run demo:queue:running-low
```

Что проговорить за 2–3 минуты:

1. P50 показывает переход `running → retrying → running`, попытка становится 2/2.
2. Новый P10 появляется в «В очереди», но не вытесняет активную попытку P50.
3. P50 окончательно падает из-за собственного JSON-шага, а не из-за нового задания.
4. Освободившийся слот немедленно получает ожидающий P10.
5. Временные метки подтверждают: `high.started_at >= low.finished_at`.

## Подготовка экрана встречи

1. Откройте `/queue` на проекторе и оставьте масштаб 80–90%, чтобы были видны все колонки.
2. В соседнем терминале задайте адрес развернутого API и ключ.
3. Запустите один кейс и не переключайтесь с монитора до завершения.
4. После анимации покажите автоматические проверки порядка, попыток и итоговых статусов в терминале.
5. Перед вторым кейсом убедитесь, что счётчики `queued` и `running` равны нулю.

Для удалённого Railway/серверного окружения:

```bash
DEMO_API_URL=https://example.up.railway.app API_KEY=<ключ> npm run demo:queue:priority-error
DEMO_API_URL=https://example.up.railway.app API_KEY=<ключ> npm run demo:queue:running-low
```

Либо непосредственно внутри Docker Compose:

```bash
docker compose exec script-factory npm run demo:queue:priority-error
docker compose exec script-factory npm run demo:queue:running-low
```

Runner в конце печатает `✓` для каждого ожидания и возвращает ненулевой exit code, если
фактический порядок, статус или код ошибки не совпали с описанием кейса. После завершения
исходное значение `max_parallel_jobs` восстанавливается.
