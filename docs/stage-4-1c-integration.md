# Этап 4: интеграция 1С и тестовая Windows-УН

Документ является готовым контрактом для разработчика 1С и инструкцией подготовки демонстрации. В примерах `TEST_UN_HOST` заменяется DNS-именем или IP тестовой УН.

## 1. Адреса и авторизация

| Назначение | Метод и адрес |
|---|---|
| Проверка УН без авторизации | `GET http://TEST_UN_HOST:33001/health` |
| Постановка задания | `POST http://TEST_UN_HOST:33001/api/v2/jobs` |
| Статус и финальный результат | `GET http://TEST_UN_HOST:33001/api/v2/jobs/{job_id}` |
| Журнал шагов | `GET http://TEST_UN_HOST:33001/api/v2/jobs/{job_id}/logs` |
| Ресурсы УН | `GET http://TEST_UN_HOST:33001/api/v2/system/resources` |
| Настройка параллельности | `PUT http://TEST_UN_HOST:33001/api/v2/system/config` |
| Интерактивная документация | `http://TEST_UN_HOST:33001/docs` |
| Монитор очереди и ресурсов | `http://TEST_UN_HOST:33001/queue` |

Для всех `/api/v2/*`, кроме `/health`, обязательны заголовки:

```http
X-API-Key: <API_KEY из .env тестовой УН>
Accept: application/json
Content-Type: application/json; charset=utf-8
```

При постановке 1С должна передавать ещё один заголовок:

```http
Idempotency-Key: <стабильный уникальный идентификатор задания 1С>
```

Повторный `POST` с тем же `uid` или `Idempotency-Key` не создаёт дубликат: API возвращает исходное задание с `idempotent: true` и HTTP 200. Новый объект возвращается с HTTP 201.

## 2. Тестовый сценарий

Готовое тело запроса находится в [`demo/stage4-1c-delay.json`](../demo/stage4-1c-delay.json). Перед отправкой 1С меняет:

- `uid` — уникальный идентификатор объекта/регистра 1С;
- `priority` — меньшее число означает более высокий приоритет;
- `context.delay_ms` — задержка без внешних действий;
- `context.input_dir` и `context.archive_dir` — каталоги из разрешённых корней УН;
- `callback.url` — опубликованный HTTP-сервис тестовой 1С.

Ключевой шаг задержки:

```json
{
  "id": "controlled-delay",
  "title": "Управляемая задержка",
  "description": "Ожидает указанное в context.delay_ms время без внешних действий.",
  "action": "wait",
  "params": {
    "duration_ms": "{{delay_ms}}"
  },
  "timeout_ms": 60000
}
```

1С может менять `context.delay_ms`, не изменяя сам шаг. `timeout_ms` шага должен быть больше задержки, а общий `timeout_ms` задания — больше суммы всех шагов и повторов. Допустимы несколько `wait` в одном сценарии.

Пример постановки:

```bash
curl -X POST http://TEST_UN_HOST:33001/api/v2/jobs \
  -H "X-API-Key: test-secret" \
  -H "Idempotency-Key: 1c-stage4-delay-001" \
  -H "Content-Type: application/json" \
  --data-binary @demo/stage4-1c-delay.json
```

Минимальный фрагмент 1С (платформа 8.3; имена прикладных процедур можно адаптировать):

```bsl
Соединение = Новый HTTPСоединение("TEST_UN_HOST", 33001);
Запрос = Новый HTTPЗапрос("/api/v2/jobs");
Запрос.Заголовки.Вставить("X-API-Key", КлючAPI);
Запрос.Заголовки.Вставить("Idempotency-Key", УникальныйИдентификатор1С);
Запрос.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8");
Запрос.УстановитьТелоИзСтроки(ТелоJSON, КодировкаТекста.UTF8, ИспользованиеByteOrderMark.НеИспользовать);
Ответ = Соединение.ВызватьHTTPМетод("POST", Запрос);
Если Ответ.КодСостояния <> 200 И Ответ.КодСостояния <> 201 Тогда
    ВызватьИсключение Ответ.ПолучитьТелоКакСтроку();
КонецЕсли;
```

В ответе нужно сохранить `job.job_id` рядом с `uid` объекта 1С.

## 3. Запрос статуса и результата

1С опрашивает `GET /api/v2/jobs/{job_id}` раз в 1–2 секунды. Не следует создавать новое задание для проверки состояния.

Статусы:

| Статус | Значение |
|---|---|
| `queued` | ожидает свободный слот с учётом приоритета |
| `running` | выполняется |
| `retrying` | ждёт повторной попытки |
| `success` | успешно, данные находятся в `result` |
| `failed` / `validation_failed` | ошибка находится в `error` |
| `timeout` | превышен тайм-аут |
| `cancelled` | отменено |

Финальные статусы: `success`, `failed`, `validation_failed`, `timeout`, `cancelled`. Результат содержит `job_id`, внешний `uid`, `un_id`, итоговый контекст, длительность и `artifacts`. Для файлов указываются имя, путь на УН, размер, MIME-тип и контрольная сумма, если она известна.

## 4. Возврат результата в 1С

Если в задании указан `callback.url`, УН после перехода в финальный статус выполняет `POST` на этот адрес. Заголовки исходящего запроса:

```http
Content-Type: application/json
Accept: application/json
Authorization: Bearer <CALLBACK_AUTH_TOKEN из .env УН>
X-Script-Factory-Event: job.completed
Idempotency-Key: <job_id>:<status>:<finished_at>
```

Тело:

```json
{
  "event_id": "job_...:success:2026-08-16T10:20:30.000Z",
  "event": "job.completed",
  "occurred_at": "2026-08-16T10:20:30.000Z",
  "job": {
    "job_id": "job_...",
    "uid": "1c-stage4-delay-001",
    "un_id": "un-test-windows-01",
    "status": "success",
    "result": {
      "job_id": "job_...",
      "uid": "1c-stage4-delay-001",
      "un_id": "un-test-windows-01",
      "context": { "waited_ms": 15000 },
      "artifacts": []
    },
    "error": null
  }
}
```

1С должна проверить Bearer-токен, сохранить событие транзакционно по `Idempotency-Key` и только затем вернуть любой HTTP 2xx. При сетевой ошибке или не-2xx УН повторяет callback с экспоненциальной паузой. Параметры `max_attempts`, `backoff_ms`, `timeout_ms` задаются в `callback`. Текущее состояние доставки доступно в `job.callback_delivery`: `pending`, `delivering`, `retrying`, `delivered` или `failed`.

Опрос статуса остаётся резервным механизмом: потеря callback не приводит к потере результата в SQLite УН.

## 5. Приоритеты и параллельность

Очередь невытесняющая: новое P10 не прерывает уже выполняющееся P50, но будет выбрано раньше ожидающих P30/P50 при освобождении слота. Число параллельных слотов меняется без перезапуска:

```bash
curl -X PUT http://TEST_UN_HOST:33001/api/v2/system/config \
  -H "X-API-Key: test-secret" -H "Content-Type: application/json" \
  -d '{"max_parallel_jobs":3}'
```

Готовый нагрузочный показ:

```powershell
$env:DEMO_API_URL = 'http://TEST_UN_HOST:33001'
$env:API_KEY = 'test-secret'
npm run demo:stage4:parallel
```

Runner создаёт три задания P50/P10/P30 с задержками 15/10/5 секунд, показывает статусы, CPU, RAM и пиковое число одновременно выполняющихся job. В `/queue` те же данные обновляются каждую секунду. Для определения границы УН повторить прогон с `max_parallel_jobs` 1, 2, 3 и далее; зафиксировать CPU, RAM, отзывчивость рабочего стола и время завершения. Рабочим лимитом считать последний уровень, при котором сотрудник может продолжать обычную работу и нет устойчивого CPU/RAM выше согласованного порога.

## 6. Файловая система

Сценариям разрешены только каталоги из `FILESYSTEM_ALLOWED_ROOTS`. На Windows пути разделяются `;`, на Linux — `:`. Попытка выйти за разрешённые корни завершается `FILESYSTEM_ACCESS_DENIED`.

| Действие | Назначение |
|---|---|
| `find_files` | поиск обычных файлов по каталогу и префиксам |
| `copy_files` | копирование найденных файлов |
| `move_files` | перенос файлов, включая перенос между томами |
| `read_text_file` | чтение текста с лимитом размера (по умолчанию 1 МиБ) |
| `write_text_file` | создание/перезапись текстового файла |
| `delete_files` | удаление; обязательно `params.confirm: true` |
| `download_files` | регистрация скачанных браузером файлов как артефактов результата |

Для демо создайте `work\incoming\TEST_STAGE4.xml`. Сценарий скопирует его в `work\archive`, а оба пути будут отражены в контексте результата.

## 7. Подготовка Windows-УН и Яндекс Браузера

1. Установить Node.js 24+, Яндекс Браузер и Git либо перенести готовый архив проекта.
2. Войти под отдельной тестовой Windows-учётной записью. Для видимого headed-браузера задача должна работать в интерактивной пользовательской сессии, а не как Windows Service в Session 0.
3. Скопировать `windows\.env.example` в `.env`, задать секреты, адрес callback 1С и разрешённые каталоги.
4. Запустить PowerShell от администратора:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\windows\preflight.ps1
.\windows\install-task.ps1
.\windows\preflight.ps1 -ExpectServiceRunning
```

Preflight проверяет Node.js, заполнение секретов без их вывода, Яндекс Браузер, порт,
запись в разрешённые каталоги и, после запуска, соответствие `UN_ID` в healthcheck.
Installer устанавливает npm-зависимости, регистрирует задачу `ScriptFactory-Test-UN`
при входе пользователя, пытается открыть TCP 33001 и запускает worker.
`windows\start-worker.ps1` автоматически находит `browser.exe` Яндекс Браузера.
При нестандартной установке задайте системную переменную
`PUPPETEER_EXECUTABLE_PATH` полным путём.

Проверки:

```powershell
Invoke-RestMethod http://localhost:33001/health
Invoke-RestMethod http://localhost:33001/api/v2/system/resources -Headers @{'X-API-Key'='test-secret'}
```

Для удалённого показа подключитесь к той же пользовательской сессии по RDP и одновременно откройте `/queue` у демонстратора. В headed-режиме виден Яндекс Браузер, а монитор показывает шаг, журнал, очередь и ресурсы. Для фонового нагрузочного теста без влияния окон на рабочий стол переключите `BROWSER_HEADLESS=true` и перезапустите задачу.

Откат установки не удаляет данные и секреты:

```powershell
.\windows\uninstall-task.ps1
# Добавьте -RemoveFirewallRule, только если правило больше не нужно.
```

Обновления следует выкладывать версиями: остановить Scheduled Task, сохранить номер
предыдущего коммита/архив релиза, заменить код, выполнить `npm ci --omit=dev`, два
preflight-прохода и только затем считать версию принятой. При неуспешном healthcheck
вернуть предыдущий каталог релиза и снова запустить задачу; `data`, `work` и `.env`
должны находиться вне заменяемого каталога либо копироваться без перезаписи.

## 8. Схема размещения

```text
1С test ──POST/GET, X-API-Key──▶ Script Factory :33001 на тестовой УН
   ▲                                      │
   └──── POST callback, Bearer token ─────┘
                                          ├── Яндекс Браузер (Puppeteer/DevTools)
                                          ├── разрешённые рабочие каталоги
                                          └── SQLite data/state.sqlite

Демонстратор ── HTTPS/VPN/RDP ──▶ /queue + интерактивный рабочий стол УН
```

Вне доверенной сети порт 33001 нельзя публиковать напрямую: нужен VPN либо reverse proxy с TLS и ограничением IP. Секреты 1С, интерфейса и callback должны отличаться.

## 9. Маршрут демонстрации (15–20 минут)

1. Показать `/health`: идентификатор тестовой УН и свободные слоты.
2. В 1С поставить P50 с задержкой 20 секунд; сохранить `job_id` из ответа.
3. Запросить статус по `job_id`, открыть ту же карточку в `/queue` и показать активный шаг `wait`.
4. Поставить P10 и P30, показать порядок выбора и одновременное выполнение при нескольких слотах.
5. На `/queue` показать CPU, RAM, слоты и журнал в реальном времени; через RDP показать Яндекс Браузер для браузерного задания.
6. Показать копирование `TEST_STAGE4.xml` и файловые пути в `result.context`.
7. Дождаться callback в 1С, сопоставить `uid`, `job_id`, `un_id`, результат и состояние `callback_delivery=delivered`.
8. На один callback вернуть 503, показать автоматический повтор с тем же `Idempotency-Key` и отсутствие дубликата в 1С.
