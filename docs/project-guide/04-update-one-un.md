# Обновить одну Windows-УН вручную

Эта инструкция не требует Git на самой УН. Используется ZIP согласованного релиза и помощник [update-one-un.ps1](tools/update-one-un.ps1). Скрипт выполняется вручную администратором; он не обновляет другие машины и не настраивает заново Scheduled Task.

## 1. Найти именно рабочую установку

В PowerShell от администратора:

```powershell
Get-ScheduledTask | Where-Object { $_.TaskName -like 'ScriptFactory*' } |
  Select-Object TaskName,TaskPath,State
Get-NetTCPConnection -LocalPort 33001 -State Listen |
  Select-Object LocalAddress,LocalPort,OwningProcess
$task = Get-ScheduledTask -TaskName 'ScriptFactory-Test-UN'
$task.Actions | Select-Object Execute,Arguments,WorkingDirectory
```

Arguments штатной задачи показывают ProjectPath и EnvFile. Не отправляйте наружу содержимое конфигурации или аргументы сторонней задачи, если там хранятся секреты. Сверьте путь с работающим node. Если задача нестандартная (ручной node, другой launcher), сначала приведите запуск к понятной задаче; помощник намеренно откажется обновлять неподтверждённый процесс.

На Баширова 07.10.2026 работали C:\script_factory, C:\script_factory\.env и ScriptFactory-Test-UN. Старые C:\ProgramData\ScriptFactory\releases/shared/debug-задачи существовали, но не были активным API. Эти исторические значения нужно проверить заново, а не копировать вслепую.

## 2. Получить и проверить архив заранее

Зафиксируйте ожидаемые version, commit и SHA-256. Разработчик может собрать полный архив из Git:

```powershell
git archive --format=zip --output C:\Temp\script-factory-release.zip COMMIT_РЕЛИЗА
if ($LASTEXITCODE -ne 0) { throw 'Не собран полный архив релиза' }
Get-FileHash C:\Temp\script-factory-release.zip -Algorithm SHA256
```

Git должен иметь все объекты выбранного commit. Ошибки fetch/archive устраняются **до остановки УН**. Для неизвестной или частично скопированной .git используйте чистый клон на компьютере разработчика; рабочую УН не сбрасывайте git reset --hard.

Альтернатива — согласованный ZIP сборки разработчика. В корне ZIP должны быть package.json, package-lock.json, src/server.js, windows/start-worker.ps1 и остальные файлы релиза. Внутри не должно быть локальных .env, data, work, node_modules или .git. Не передавайте в помощник ZIP GitHub с обёрткой «repo-commit/»: сначала подготовьте архив с файлами прямо в корне.

Скопируйте архив, его контрольную сумму и update-one-un.ps1 на УН. Не берите SHA из скачанного подозрительного архива как единственное доказательство: сравните с суммой согласованной сборки.

## 3. Подготовить окно обслуживания

1. Приостановите отправку новых заданий из 1С на эту УН; согласуйте это с остальными клиентами API.
2. Дождитесь running=0 и queued=0 в /health.
3. Проверьте/сохраните локальные правки исходников, если они есть. .env, данные и XML нельзя заменять шаблоном.
4. Убедитесь, что worker-пользователь залогинен, а Node 24+ и npm.cmd доступны администратору.
5. Проверьте свободное место: нужна копия кода, DATA_DIR (включая артефакты) и, при смене зависимостей, старые/новые node_modules.

Сохранённая конфигурация и база могут содержать секреты/деловые данные: резервные копии остаются на этой УН в административном каталоге, не загружаются в Git.

## 4. Запустить обновление

Пример — замените путь ZIP, SHA и версию согласованными значениями:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\Temp\update-one-un.ps1 `
  -ProjectPath C:\script_factory `
  -EnvFile C:\script_factory\.env `
  -TaskName ScriptFactory-Test-UN `
  -TaskPath '\' `
  -Port 33001 `
  -PackageZip C:\Temp\script-factory-release.zip `
  -ExpectedVersion 'ВЕРСИЯ_РЕЛИЗА' `
  -ExpectedSha256 'SHA256_СОГЛАСОВАННОГО_АРХИВА' `
  -BackupRoot C:\ScriptFactory-backups `
  -ConfirmNoNewJobs `
  -ConfirmReplaceCode
```

ConfirmNoNewJobs подтверждает, что вы приостановили новые задания; сама очередь не блокирует новые POST. ConfirmReplaceCode подтверждает просмотр локальных изменений. Если не знаете фактический EnvFile/TaskPath, не запускайте команду.

Что выполняет помощник:

- Проверяет SHA, корень/безопасность ZIP, package.version, Node, конфигурацию, текущий /health, UN_ID, задачу и точный PID слушателя.
- Готовит код в staging. При изменении lockfile-зависимостей выполняет npm.cmd ci там, пока старый сервис работает. Если изменился только номер версии, сохраняет имеющиеся node_modules.
- Сохраняет копию заменяемых файлов и manifest.json. Повторно проверяет пустую очередь.
- Останавливает задачу и проверенный дочерний node; убеждается, что порт больше не слушается.
- Копирует фактический EnvFile и фактический DATA_DIR, включая SQLite WAL/SHM, после остановки процесса.
- Накладывает код, при необходимости заменяет подготовленные зависимости, запускает прежнюю задачу.
- Проверяет точную version, release_date, ready и UN_ID. При сбое возвращает старый код/зависимости и проверяет готовность старой версии.

Результат — JSON с updated=true, version, ready, un_id и backup. Если ошибка возникла до остановки, текущая установка не меняется. Если после остановки — в ошибке указано, удалось ли вернуть старую готовую версию.

Метод ZIP накладывает файлы, не переключает Git HEAD и не удаляет устаревшие файлы, которых нет в архиве. .git не обновляется: git status может показывать изменения релиза. Не выполняйте после этого git checkout/reset, считая старую .git источником установленной версии; сверяйте package.json и manifest. Для релиза, требующего удаления старых модулей/миграции базы, разработчик должен добавить отдельный проверенный план, а не полагаться на overlay.

## 5. Проверить поведение, затем вернуть задания

```powershell
$h = Invoke-RestMethod http://127.0.0.1:33001/health -TimeoutSec 10
$h | Select-Object status,ready,version,release_date,un_id
```

Сверьте точную версию с архивом. Затем отправьте [smoke-workflow](examples/smoke-workflow.json) по [шпаргалке API](06-api-1c.md): требуется success, result.Rezult_1 и артефакт с filename/api_url, который скачивается. Для СБИС дополнительно проверьте ip-check. В версии 0.6.17+ ответ содержит ip при успешной проверке.

Не отправляйте реальные отчёты и не подключайте рабочий callback ради проверки обновления. После безопасной проверки разрешите 1С снова ставить задания. Сам помощник проверяет запуск сервиса, но не выполняет бизнес-сценарий СБИС.

## 6. Ручной откат после неудачной проверки

Если помощник сам вернул старую готовую версию, повторный откат не нужен. Для сбоя, выявленного после его успешного завершения:

1. Снова запретите новые задания, дождитесь пустой очереди и остановите задачу/её точный node так же, как при обновлении. Не копируйте SQLite при работающем listener.
2. Откройте backup/manifest.json: он содержит project_path, env_file, data_dir, old_version и список заменённых файлов.
3. Для каждого files восстановите backup/code/FILE в project_path/FILE. Если файла не было в backup/code, это добавленный новым релизом файл: удаляйте только этот конкретный файл.
4. Если dependencies_changed=true, сохраните новые node_modules отдельно, верните backup/node_modules. Если автоматический откат уже переместил старые зависимости обратно, резервной папки может не быть.
5. Запустите прежнюю задачу, проверьте exact old_version и ready, выполните безопасное задание.

DATA_DIR автоматически не восстанавливается поверх новых заданий. Если релиз изменил схему SQLite, заранее согласуйте совместимый откат; восстановление backup/data допустимо только с остановленным worker и пониманием, какие новые результаты будут потеряны. saved.env восстанавливайте лишь если конфигурация действительно изменена; обычное обновление её не меняет.

## Почему старая инструкция могла не сработать

Она предполагала полноценный Git-клон и стандартный data внутри проекта, проверяла состояние Scheduled Task вместо завершения listener и не учитывала отдельный EnvFile. В Windows также есть npm.ps1/ExecutionPolicy и BOM в JSON. Новый путь проверяет реальную установку, использует ZIP, npm.cmd и копирует базу после остановки node.
