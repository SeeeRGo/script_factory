# Спящий режим незанятой УН: Windows-модуль и API для 1С

Версия API: 0.7.1. Основная целевая ОС — Windows Server 2022; используются общие Windows API, доступные также в Windows 10 20H2 и Windows 11. Подтверждённые испытания и ограничения приведены ниже.

## Что установлено и как работает в фоне

Модуль входит в существующий сервис Script Factory. Отдельно устанавливать Windows-службу, .NET SDK или PowerShell 7 не требуется: используются Node.js существующего API, встроенный Windows PowerShell 5.1, .NET Framework и Windows WTS/PowrProf API. Браузер и ЭЦП остаются в пользовательском сеансе.

Когда API работает, модуль может периодически проверять условия без открытой 1С и без отдельной команды из неё. Если API остановлен, проверки не выполняются. Существующая задача запуска API должна работать: текущий установщик запускает её при входе пользователя. После перезагрузки УН для браузерной автоматизации по-прежнему требуется пользовательский сеанс; новый модуль не настраивает автологин и не меняет учётную запись задачи.

Один и тот же алгоритм вызывается таймером и методом API:

1. Если есть queued, running или retrying, переход не выполняется. Проверяется также завершение выполняющихся обработчиков, а не только статус задания.
2. Пока передаются артефакты или выполняется/ожидается повтор callback, переход откладывается. Исчерпанные попытки доставки callback не блокируют сон навсегда; результат остаётся на диске в рамках обычного срока хранения.
3. Через Windows WTS перечисляются локальные и RDP-сеансы, включая отключённые RDP. Исключаемая учётная запись сопоставляется по SID; при одинаковом имени в разных доменах это разные пользователи. По умолчанию исключается пользователь API. Исключение относится ко всем сеансам указанного пользователя: не используйте эту учётную запись для ручной работы, которую нужно защищать от сна.
4. Каждый другой пользователь должен бездействовать строго дольше user_idle_seconds. Равенство порогу ещё блокирует сон. Если других пользователей нет, это условие выполнено. Неизвестные состояния, отсутствующее время ввода или ошибка чтения сеансов блокируют сон.
5. Проверяются поддержка выбранного режима Windows (`sleep` или `hibernate`) и право SeShutdownPrivilege. Затем выдерживается grace_seconds и повторяется проверка.
6. На финальном этапе закрывается приём новых заданий, состояние очереди сохраняется в SQLite. Нативный Windows-компонент ещё раз проверяет пользователей непосредственно перед SetSuspendState: первый аргумент false для sleep и true для hibernate.
7. Выполняется явно выбранный режим Windows с сохранением событий пробуждения. По умолчанию mode=sleep; с API 0.7.1 можно явно выбрать mode=hibernate (S4). Автоматической подмены режима, shutdown, принудительного выхода пользователей и закрытия приложений нет. После возврата из Windows приём заданий возобновляется; выдерживается resume_cooldown_seconds перед следующим сном.

Новое задание во время отсрочки отменяет текущую проверку. Новое задание после начала финального перехода получает 503 POWER_TRANSITION_IN_PROGRESS: 1С может повторить запрос после пробуждения или выбрать другую УН. В этом состоянии /health также сообщает неготовность. Изменение настроек и вызов cancel отменяют проверку до финального перехода. Условия повторно проверяются после асинхронных операций, чтобы не уснуть с уже принятой работой.

Модуль не выключает питание и не является средством пробуждения. Во время сна API недоступен. Способ пробуждения определяется инфраструктурой; для проверки полного цикла должен быть обеспечен способ вернуть УН в работу. Отдельный согласованный односторонний тест может закончиться недоступностью УН до ручного включения; это не подтверждает автоматическое пробуждение.

## Где хранятся пользователь и время бездействия

Исходные значения берутся из `.env`. Явные переопределения через API сохраняются на конкретной УН в `DATA_DIR/power/config.json` и имеют приоритет над `.env` для соответствующих полей. Остальные значения продолжают браться из .env/автоматического определения. Перезапуск API не сбрасывает переопределения. Для изменения ранее переопределённого поля используйте PATCH. Возврат к значениям .env: остановить API при пустой очереди, сохранить резервную копию config.json, убрать этот файл и запустить API.

```dotenv
POWER_MODE=sleep
POWER_ENABLED=false
POWER_BACKGROUND_ENABLED=false
POWER_DRY_RUN=true
POWER_EXCLUDED_USER=
POWER_USER_IDLE_SECONDS=1800
POWER_CHECK_INTERVAL_SECONDS=60
POWER_GRACE_SECONDS=30
POWER_RESUME_COOLDOWN_SECONDS=300
```

| Поле API | Значение | Смысл |
| --- | --- | --- |
| mode | sleep | POWER_MODE: sleep или hibernate; выбор явный, без автоматической подмены. |
| enabled | false | Разрешить модуль; при false ручной вызов возвращает 503 POWER_DISABLED |
| background_enabled | false | Автоматические периодические проверки; не требуется для ручного вызова |
| dry_run | true | Проверять условия и писать журнал, но не вызывать suspend |
| excluded_user | пользователь API | Исключаемая Windows-учётная запись; предпочтительно COMPUTER\User или DOMAIN\User |
| user_idle_seconds | 1800 | Порог бездействия каждого другого пользователя, 1–2592000 секунд |
| check_interval_seconds | 60 | Интервал фоновых проверок, 5–86400 секунд |
| grace_seconds | 30 | Задержка с повторной проверкой, 0–3600 секунд; для эксплуатации рекомендуется ненулевая |
| resume_cooldown_seconds | 300 | Задержка после возврата из suspend или ошибки его вызова, 1–86400 секунд |

Если POWER_EXCLUDED_USER пуст и excluded_user не переопределён через API, при смене учётной записи запуска API с Robot на Robot2 и перезапуске исключение автоматически следует за новым пользователем. Явно заданный excluded_user сохраняется, пока его не изменят. PATCH с excluded_user=null убирает переопределение API и возвращает исходное значение из .env; при пустом POWER_EXCLUDED_USER это автоматический выбор пользователя API. Настройка excluded_user не меняет пользователя процесса: Windows-компонент в текущем режиме наследует учётную запись API. Пароли пользователей в настройках модуля не хранятся. Новому пользователю нужны права на DATA_DIR и необходимые Windows-привилегии.

Файл конфигурации записывается атомарно; одновременные изменения разных полей не теряются. Повреждённый config.json нужно исправить перед запуском сервиса — он не будет молча заменён разрешающими настройками.

## Методы API

Все методы используют существующий `X-API-Key`. Произвольные команды Windows, имя программы или скрипт через эти методы передать нельзя.

| Метод | Назначение |
| --- | --- |
| POST /api/v2/system/power/suspend | Принять запрос запуска алгоритма |
| GET /api/v2/system/power/config | Получить действующие настройки |
| PATCH /api/v2/system/power/config | Изменить и сохранить настройки без перезапуска |
| GET /api/v2/system/power/status | Необязательная диагностика: настройки, выполняемая проверка, последнее решение |
| GET /api/v2/system/power/sessions | Диагностика Windows-сеансов, возможностей sleep и привилегии |
| POST /api/v2/system/power/cancel | Отменить текущую проверку/отсрочку; будущие фоновые проверки остаются включёнными |

Ручной вызов принимает пустой JSON-объект `{}`. Ответ отправляется до запуска проверок:

```json
{"status":"accepted"}
```

HTTP 202 означает только доступность метода и принятие вызова. Он не подтверждает сон: при занятой очереди или активном пользователе алгоритм ничего не сделает. В 1С не требуется получать результат решения. Метод не создаёт job_id или Rezult_N, не ждёт сна и не посылает callback о факте сна. Повторные вызовы во время текущей проверки объединяются, отдельная очередь таких запросов не создаётся.

Ошибки вызова: 400 — неверное тело; 401 — неверный ключ; 503 — модуль отключён, ОС не поддерживается или начался финальный переход. Для изменений/отмены, начатых до финальной блокировки, возможен 409 при попытке завершить их во время перехода. Причины самого решения доступны только в диагностике и журнале.

Пример настройки без реального сна:

```json
{
  "enabled": true,
  "background_enabled": true,
  "dry_run": true,
  "excluded_user": "UN-01\\Robot",
  "user_idle_seconds": 1800,
  "check_interval_seconds": 60,
  "grace_seconds": 30
}
```

Для разрешения реального сна после проверки измените dry_run на false. Чтобы остановить только фоновый режим, задайте background_enabled=false. Чтобы запретить также ручные запросы, enabled=false. GET sessions выполняет только диагностику даже при отключённом модуле.

## Вызов из 1С

Иллюстрация для адаптации; в реальной конфигурации 1С этот код не запускался:

```bsl
Запрос = Новый HTTPЗапрос("/api/v2/system/power/suspend");
Запрос.Заголовки.Вставить("X-API-Key", КлючAPI);
Запрос.Заголовки.Вставить("Content-Type", "application/json");
Запрос.УстановитьТелоИзСтроки("{}", КодировкаТекста.UTF8);
Ответ = Соединение.ВызватьHTTPМетод("POST", Запрос);
Если Ответ.КодСостояния = 202 Тогда
    // Вызов принят. Не делаем вывод о том, уснула ли УН.
Иначе
    // Обработать недоступность/ошибку вызова по коду HTTP и телу ответа.
    Сообщить(Ответ.ПолучитьТелоКакСтроку());
КонецЕсли;
```

1С может по своему регламенту вызывать метод для каждой УН. Альтернативно один раз включается фоновый режим на УН; дальнейшие проверки выполняются самим API. Настройки изменяются тем же HTTPСоединением через PATCH /api/v2/system/power/config с JSON-полями из таблицы.

## Массовое внедрение

1. Подготовить пакет API 0.7.0+ с каталогами src/windows и остальными файлами проекта. Не включать .env, data, work или node_modules с другой машины. На УН уже должны быть установлены зависимости проекта. Использовать [инструкцию обновления](04-update-one-un.md), штатный update-one-un.ps1 и существующую задачу запуска. Дополнительная служба для модуля не создаётся. Обновлять при пустой очереди с резервной копией.
2. Раздать пакет штатными средствами организации: GPO, системой управления рабочими местами или существующим механизмом развёртывания. .env, DATA_DIR и учётную запись API сохранить.
3. Заполнить CSV по [примеру](../../windows/power-inventory.example.csv). В CSV хранится имя переменной окружения с API-ключом, а не сам секрет. Пустое ExcludedUser сохраняет текущую настройку или пользователя API по умолчанию.
4. Выполнить [массовую настройку](../../windows/configure-power-fleet.ps1) сначала в dry-run. Скрипт не меняет сертификаты TLS, не отключает их проверку и не перезапускает сервис. Сначала всегда применяется dry-run; с EnableSleep дополнительно проверяются нативные возможности и привилегия Windows, и только затем разрешается реальный сон. При отсутствии поддержки реальный сон не включается.

```powershell
# UN_01_API_KEY и UN_02_API_KEY заранее заданы в окружении оператора.
.\windows\configure-power-fleet.ps1 -InventoryCsv .\inventory.csv -Background -UserIdleSeconds 1800 -ResultCsv .\power-results.csv
```

Сначала можно добавить `-WhatIf`: сетевые изменения не выполнятся. После проверки журналов и поддержки сна повторить с `-EnableSleep`, если нужен реальный автоматический сон. Для режима только по команде 1С не указывать `-Background`. Отчёт массовой настройки отражает только успех настройки, а не состояние сна.

На каждой УН проверяйте GET sessions: Windows/API-учётной записи нужны чтение сеансов других пользователей и SeShutdownPrivilege. Ранее установленная задача Highest сама по себе не выдаёт отсутствующие права обычному пользователю. Модуль не выдаёт их автоматически и не переводит браузер в SYSTEM. Защитите ACL каталога установки и файлов настроек от изменения посторонними.

## Диагностика и ограничения

Журнал решений — `DATA_DIR/power/events.jsonl`, ротация при размере около 1 МиБ в events.jsonl.previous. GET status возвращает последнее решение текущего запуска. Основные причины: JOBS_PENDING, USER_ACTIVE, SESSION_DATA_UNAVAILABLE, SUSPEND_UNSUPPORTED, HIBERNATE_UNSUPPORTED, POWER_PRIVILEGE_MISSING, CALLBACK_PENDING, ARTIFACT_TRANSFER, CHECK_CANCELLED, RESUME_COOLDOWN. В dry-run при выполненных условиях — WOULD_SUSPEND. Событие suspending означает начало запроса ОС, а resumed — возврат из успешного вызова Windows; отдельного доказательства длительности физического сна это не даёт.

Windows Server 2022 или Windows 10/11 сами по себе не гарантируют поддержку sleep/hibernate. Она зависит от оборудования, ACPI, драйверов и виртуализации. Для mode=sleep при отсутствии S1/S2/S3 или подходящего S0 low-power idle возвращается SUSPEND_UNSUPPORTED. Для mode=hibernate требуется доступный S4 и файл гибернации; иначе HIBERNATE_UNSUPPORTED. Приостановка ВМ через гипервизор не реализована. Настройки Windows модуль не изменяет: он не создаёт файл гибернации автоматически.

Время последнего ввода не доказывает отсутствие любой фоновой программы пользователя. Критерий этого алгоритма — очередь API и пользовательский ввод; период ручного обслуживания можно защитить отключением enabled/background_enabled. При недоступных сведениях решение всегда запрещающее.

Проверки: модульные проверки очереди/сеансов/отмены/финальной блокировки, фонового режима, конкурентных настроек, dry-run; HTTP-проверки 202 до анализа, авторизации, валидации и сохранения настроек при перезапуске. Реальный suspend требует отдельной эксплуатационной проверки с обеспеченным пробуждением. Проверка Windows 10 20H2 и Windows 11 на физических/виртуальных машинах пока не выполнена.

### Испытание на доступной тестовой УН

15.10.2026 выполнен изолированный запуск API 0.7.0 на Windows 10 Pro for Workstations 22H2, build 19045. Нативный C#-компонент скомпилирован встроенным PowerShell, прочитаны два WTS-сеанса, проверены смена исключаемой учётной записи и ответ 202. Получены ожидаемые блокировки USER_ACTIVE и SUSPEND_UNSUPPORTED. Рабочие .env и задача запуска не изменены. На этой гостевой системе Windows не предоставляет поддерживаемого состояния sleep; фактический сон не выполнялся. Проверка не является испытанием Server 2022 или Windows 10 20H2. Ранее указанная УН Server 2022 в момент проверки была недоступна.


## Гибернация на QEMU-госте (API 0.7.1+)

16.10.2026 на доступных QEMU-УН powercfg /a показал блокировку S3 графическим компонентом и недоступность гибернации из-за типа файла. На одной тестовой УН после `powercfg /hibernate /type full` Windows подтвердила S4 и наличие файла гибернации. Это отдельная административная настройка, не действие API и не гарантия успешного восстановления.

До настройки сохраните вывод `powercfg /a`, значения HibernateEnabled/HiberFileType/HiberFileSizePercent из HKLM\SYSTEM\CurrentControlSet\Control\Power и проверьте место на системном диске. Полный файл занимает дополнительное место. Для возврата к сокращённому файлу (быстрый запуск) используется `powercfg /hibernate /type reduced`; не выключайте гибернацию целиком, если она была включена ранее.

Пример явной настройки через PATCH /api/v2/system/power/config:

```json
{"mode":"hibernate","enabled":true,"background_enabled":false,"dry_run":true,"excluded_user":"Robot","user_idle_seconds":1800}
```

Проверьте GET sessions: hibernate_supported=true, suspend_privilege=true и корректные времена всех остальных пользователей. Сначала выполните dry-run. Для согласованного реального испытания измените только dry_run=false и вызовите тот же POST /api/v2/system/power/suspend с `{}`. Результат вызова для 1С по-прежнему 202 accepted; mode передаётся в настройках, не в POST. Фоновый режим включается отдельно.

Для массовой настройки используйте configure-power-fleet.ps1 с `-PowerMode hibernate`; `-EnableSleep` в этом скрипте означает снятие dry-run для выбранного режима. Он проверяет именно hibernate_supported при выборе гибернации. Полный файл заранее настраивается администратором на каждой УН.

Пропадание RDP/API после команды является признаком остановки, но само по себе не отличает гибернацию от сетевого сбоя. Для полной приёмки нужны событие Windows о переходе в S4/статус ВМ в панели и проверка восстановления. Гибернация не заменяет внешний механизм включения виртуальной машины.


### Практическая проверка 0.7.1 от 16.10.2026

На одной Windows 10 20H2 / QEMU-УН рабочий API обновлён с 0.6.18 до 0.7.1 с резервной копией. Хеш .env и XML задачи запуска не изменились; зависимости не менялись. Windows после настройки полного файла подтвердила hibernate_supported=true. Нативный helper выполнялся от пользователя API и корректно прочитал время ввода второго пользователя.

По установленному API проверены: блокировка USER_ACTIVE; затем после бездействия dry-run с WOULD_SUSPEND. Реальный POST вернул 202 accepted, в журнале зафиксирована отсрочка с повторной проверкой. После неё существующее RDP-соединение завершилось, внешняя проверка перестала получать протокольный ответ RDP, тогда как контрольная УН продолжила отвечать. TCP-проброс оставался открытым, поэтому один TCP connect не использовался как критерий доступности.

Это успешный односторонний тест по согласованному критерию недоступности УН. Событие Windows о фактическом S4, состояние в панели гипервизора и восстановление не проверены. Копирование последнего диагностического JSON через RDP оборвалось при переходе; локальная копия на УН сохранялась до сетевой. Не считать недоступность самостоятельным доказательством сохранности сеансов после восстановления.

На тестовой машине оставлен ручной режим: mode=hibernate, background_enabled=false, dry_run=false, user_idle_seconds=30, grace_seconds=10, excluded_user — учётная запись API. Короткий порог предназначен для теста. Перед эксплуатацией задайте рабочий порог (например 1800 секунд); фоновые проверки включайте отдельно. При включении УН этот режим не вызывает повторную гибернацию сам по себе, поскольку background_enabled=false.
