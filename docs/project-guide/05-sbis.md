# Индивидуальные параметры СБИС и правила ui

Сценарий: [demo/sbis-report-full.json](../../demo/sbis-report-full.json), версия 3.4.0, формат json-workflow, минимальный сервис 0.9.4 (действие browser_tab). В 0.6.17 добавлены поля API; в 0.6.19 — минимальный запуск браузера из JSON.

## Основные значения

| Параметр | Тип / по умолчанию | Значение |
| --- | --- | --- |
| inn | Строка / null | ИНН организации, 10 или 12 цифр, обязателен |
| mode | Строка / validate_only | preflight: вход/переходы/сверка без импорта; upload_only: импорт без проверки, подписи и отправки; validate_only: импорт/проверка без отправки; send: допускает отправку |
| submit_enabled | Boolean / false | Отправка разрешена только вместе с mode=send, успешной проверкой и настроенными шагами отправки |
| root_dir | Строка / null | Каталог исходных XML на УН, в разрешённых корнях |
| loaded_dir | Строка / null | Существующий каталог архивирования подтверждённых отправок; не используется для перемещения в validate_only |
| allow_multiple | Boolean / true | Несколько самостоятельных отчётов одного ведомства; не означает поддержку частей одного комплекта |
| authority_prefixes | Массив | Один–три объекта {authority,prefixes,bundle_files?,ui?}; ведомство нельзя повторять |
| authority / prefixes | Код / массив | Используются только при authority_prefixes=null; одного изменения этих полей недостаточно при заданном массиве |

В версии 3.2.0 без bundle_files выбираются все XML, соответствующие любому переданному префиксу. Отсутствующие префиксы и ведомства пропускаются. Совпадение одного пути с несколькими префиксами внутри ведомства не дублирует отчёт; выбор одного пути для двух ведомств запрещён. Префиксы регистрозависимы. files_list не обходит подкаталоги.

Если подходящих XML нет, задание завершается успешно: в проекции результата нет Rezult_N, artifacts пуст; браузер и проверка IP не запускаются, файлы результата и снимки не создаются. Это не скрывает ошибки недоступного каталога, запрета файлового доступа или неполного найденного комплекта. При наличии файлов UI проверяется только для ведомств с найденными отчётами. Каждый самостоятельный отчёт получает отдельный плоский Rezult_N; комплект связанных XML получает один элемент с file_count. Новый JSON нужно передавать в script_text: обновление сервиса само не заменяет текст сценария в 1С.

## Соответствие вашей таблице

| Контролирующий орган | Код | Префиксы |
| --- | --- | --- |
| ФНС | FNS | NO_BOUPR, NO_NDFL3 |
| СФР | SFR | POVD |

Это два объекта, а не три; два префикса ФНС объединяются. Росстат не добавляется без соответствующих отчётов. [Пример входных данных](examples/sbis-input.example.json) — только context, не готовый API-запрос. Префиксы не подтверждают валидность XML или готовность экранных привязок.

## Общий ui и ui ведомства

context.ui — общие адреса, селекторы, шаги и проверки экранов. authority_prefixes[].ui переопределяет отдельные поля для ведомства. Итог вычисляется как `{...context.ui, ...plan.ui}`: при совпадении побеждает настройка ведомства; массив/вложенный объект заменяется целиком.

В ui находятся, например, organization_steps, organization_selector, upload_steps, validate_steps, validation_status_selector, protocol_selector, validation_success_text, validation_failure_text, reopen_steps, submit_steps и sent_status_selector. Это технический профиль экрана, а не название госоргана или префикс XML.

Важны два разных уровня замены:

1. context задания поверхностно заменяет context сценария. Новый authority_prefixes заменяет весь массив, включая вложенные ui старых элементов.
2. Уже внутри сценария каждый plan.ui поверхностно дополняет общие context.ui.

В полном JSON 3.0.0 общие привязки импорта, кнопки проверки и зелёной/розовой панели заполнены и проверены для РСВ ФНС и ЕФС-1 СФР. Для этих экранов можно передать authority_prefixes без ui: будут использованы общие значения. Поля ui в элементах ФНС/СФР дублируют профиль проверки; для другого интерфейса переопределите нужные значения. Это не подтверждение других видов отчётов или настоящего XML Росстата.

Предпочтительно хранить ui в шаблоне, а в 1С менять бизнес-поля. Отдельного автоматического слияния нового массива с прежними plan.ui нет. Если используете специальные переопределения ведомства, перенесите их в новый массив. Для общих проверенных привязок это не требуется.

| validation_timeout_ms | 300000 | Ожидание проверки, 1–900000 мс; дополнительно ограничено заданием |

| submit_timeout_ms | 300000 | Ожидание отправки, 1–900000 мс; дополнительно ограничено заданием |
| login_url / report_url / authenticated_url | Адреса СБИС/Saby | Вход, отчётность, подтверждённый кабинет; обычно оставить шаблонные |

Не передавайте служебные submission_started, plans, reports и промежуточные результаты как индивидуальные параметры. Результаты для 1С — отдельные плоские job.result.Rezult_N для каждого самостоятельного отчёта (комплект XML — один отчёт); коллекций внутри них нет. В каждом есть inn, authority и section_name. section_name заполняется после подтверждённого импорта, до него null. Текст проверки — отдельный артефакт. Версия сценария 3.0.0 создаёт `result-N.json` с объектом всех Rezult_N. При повторной финализации появляется следующий номер; берите последний JSON результата из массива artifacts. Сохранённая панель ошибок не является официальной квитанцией ведомства.

## Что пока нельзя считать готовым

В предыдущем кабинете проверены preflight ФНС/СФР/Росстата, выбор раздела и сверка организации. Реальный импорт и сохранение текста ошибок проверены для тестовой НДС ФНС. На дополнительной УН 12.10.2026 импортирован РСВ ФНС, подтверждены исходный файл, полный ИНН из видимого поля и ключ карточки; СБИС показал «Ошибки не найдены», текст проверки сохранён на УН. ЕФС-1 СФР тоже импортирован и успешно проверен с подтверждением полного ИНН и ключа; текст проверки сохранён на УН. NO_BOUPR, NO_NDFL3 и POVD требуют соответствующих XML и проверок экранов.

12.10.2026 переход к отправке обоих отчётов открыл окно отсутствующей лицензии «Отчетность»: доступная «Нулевая отчетность» не позволяет отправить эти отчёты с ненулевыми показателями. Подпись и реальная отправка обоих отчётов не выполнялись. Покупка и оформление лицензии в долг не выполнялись; для проверки конечного этапа нужна подходящая лицензия кабинета.

Если два самостоятельных элемента открывают одну карточку, возвращается REPORT_BUNDLE_REQUIRED. Для связанных XML используйте явный bundle_files, описанный ниже. После отправки без подтверждённого исхода требуется сверка с сайтом, а не автоматический повтор.

В новом кабинете ИП подтверждены вход, ссылка организации и preflight ФНС/СФР с повторной сверкой полного ИНН. Это отдельная проверка нового UI-профиля. Файл NO_RASCHSV не следует автоматически относить к СФР: для проверенного XML КНД 1151111 соответствует РСВ ФНС; ЕФС-1 в формате ЭДСФР — отдельный отчёт СФР.

Для send обязательна ui.current_card_scope_selector — полная текущая карточка вместе с её статусом. Для проверенного интерфейса используется .controls-StackTemplate:has(.report-theme__contrastWrapper). После шагов отправки ИНН и прежний ключ сверяются повторно. Единственное окно отсутствия лицензии и статус «Отчет создан» внутри этой карточки дают REPORTING_LICENSE_REQUIRED и Rezult_1.state=license_required. Другая карточка или противоречащий статус сохраняют requires_reconciliation; покупка, повтор и архивирование не выполняются. 13.10.2026 конечные статусы отправки и «Отчет сдан» подтверждены для обоих отчётов и привязаны в JSON 2.0.3.


## Текущее состояние после 13.10.2026

Датированный отказ лицензии 12.10 описывает предыдущий прогон. После отдельного разрешения пользователя на «В долг» РСВ и ЕФС-1 реально подписаны и отправлены; повторное чтение карточек подтвердило «Отчет сдан». Архивированы рабочие копии и протоколы проверки, создан общий JSON результата. Подтверждение получено по статусу СБИС, файлы квитанций отдельно не скачивались.

Сценарий 3.4.0 требует API 0.9.4+. В send при нескольких отчётах одного ведомства каждый импортируется в отдельной именованной вкладке общей авторизованной сессии. Сначала проверяются все отчёты ведомства; затем сценарий выбирает сохранённую вкладку каждого XML, сверяет полный ИНН и ключ карточки, повторяет проверку и отправляет. После подтверждённой отправки и архивирования вкладка закрывается. Стандартный ui.reopen_steps оставляет эту карточку открытой; дополнительные привязки поиска карточек в списке не требуются. Закрытая или отсутствующая вкладка вызывает ошибку BROWSER_TAB_NOT_FOUND до отправки. Список ui.sent_status_texts содержит проверенные варианты отправки и приёма, а в sbis_status записывается фактический текст.

Предупреждение о лицензии в долг не закрывается как обычная подсказка. Без отдельного Boolean license_debt_enabled и согласованной license_debt_expected_amount оно останавливает отправку с понятным кодом. Нельзя автоматически согласовывать финансовые условия по показанной сайтом цене. ROSSTAT с настоящим XML по-прежнему не проверен. Проверка комплекта НДС описана ниже.

Финансовые данные в новом результате плоские: license_requires_confirmation, license_amount, license_currency, license_continuation. Ошибка конкретного отчета находится в error_code/error_message; статус задания и общая ошибка остаются в job.status/job.error. Старые результаты версии 2.0.3 не преобразуются.


### Отчёт из нескольких XML (сценарий 3.1 / API 0.8)

В элементе `authority_prefixes` можно явно включить `bundle_files: true`:

```json
{
  "mode": "upload_only",
  "submit_enabled": false,
  "authority_prefixes": [{
    "authority": "FNS",
    "prefixes": ["NO_NDS_", "NO_NDS.8_", "NO_NDS.9_"],
    "bundle_files": true
  }]
}
```

Первый префикс выбирает основной XML. Остальные задают обязательные типы частей. Имена частей берутся из ссылок внутри основного XML, а не по совпадению UUID или дате изменения: UUID разных частей могут отличаться. Все файлы должны находиться непосредственно в `root_dir`. Отсутствующая ссылка или часть останавливает задание до импорта. При `bundle_files: false` (по умолчанию) сохраняется выбор самостоятельных отчётов по префиксам.

Универсальное действие `file_read` читает только разрешённый файл с проверкой SHA-256; разбор ссылок и выбор частей выполняются выражениями самого JSON. Для основного XML используется windows-1251 и предел 1 МиБ. Проверки файла и разрешённых каталогов нельзя отключать.

Комплект формирует один плоский `Rezult_N`, включая `file_count`, `bundle_verified`, `file_name_1`, `sha256_1` и аналогичные поля остальных частей. `bundle_verified` подтверждает подбор исходных частей и их контрольные суммы; подтверждение импорта дополнительно зависит от интерфейса СБИС. `upload_only` возвращает `uploaded_not_sent` после подтверждения карточки, не запускает проверку и не перемещает исходники. Архивирование частей допускается только после подтверждённой отправки; при частичной ошибке перемещения нужна сверка каталогов.

Повторный запуск импорта не является продолжением уже загруженной карточки. После неоднозначного исхода сначала сверьте существующий черновик в СБИС; не создавайте повторное задание с отправкой вслепую.

19.10.2026 на новой УН Windows Server 2022 подтверждён запуск через API 0.8.0 в Яндекс Браузере: основной НДС и две связанные книги выбраны одним комплектом, импортирована карточка с подтверждённым ИНН и ключом, получен один плоский Rezult_1 со статусом uploaded_not_sent и file_count=3. Проверка содержания всех разделов, подпись и отправка этого комплекта не выполнялись. Метаданные и диагностические артефакты прогона не входят в Git. [Пример context](examples/sbis-bundle-upload.example.json) требует замены ИНН; это не готовый запрос POST /api/v2/jobs.


## Как найти шаг по журналу

«Шаг 58/58» — динамический номер выполненного шага, включая циклы, if и вызовы routines. Это не номер элемента верхнего массива steps и не окончательное число шагов. После ошибки могут идти шаги on_error, сохраняющие результат.

У каждого шага JSON 3.2.0 есть постоянный id и название. В GET /api/v2/jobs/{job_id} найдите execution.steps[57] (индекс с нуля) и прочитайте id, title, description. Если шаг есть в on_error или вызывается в цикле, один id может встречаться в нескольких выполнениях. Ищите этот id в исходном script_text именно данного задания. API 0.9.3 также записывает step_title и source_path в сообщения журнала, включая ошибку; source_path, например routines.identity[0], непосредственно указывает элемент JSON. Эти поля требуют обновления API; новая логика поиска файлов требует только JSON 3.2.0 и работает на API 0.8.0+.

Ошибка browser_wait «Waiting failed: 30000ms exceeded» означает, что за 30 секунд не выполнилось выражение params.expression соответствующего шага. Причину определяют по самому выражению и состоянию страницы. Один номер без job_id не определяет, какое условие ожидалось.

## Три XML НДС

Для основного NO_NDS_ и связанных NO_NDS.8_ / NO_NDS.9_ используйте один элемент FNS с prefixes: ["NO_NDS_", "NO_NDS.8_", "NO_NDS.9_"] и bundle_files: true. NO_NDS без подчёркивания совпадает со всеми тремя именами; без bundle_files они ошибочно выбираются как самостоятельные отчёты. Части определяются по ссылкам основного XML, а не только по имени. Отсутствие основного файла пропускается; если основной найден, но его обязательная часть отсутствует, возвращается ошибка комплекта. Для нескольких основных файлов обрабатывается каждый найденный комплект.




В API 0.9.3 текст ошибки JSON workflow также содержит название исходного шага: `Шаг «Дождаться списка подписей либо завершения автоматического входа»: Waiting failed: 30000ms exceeded`. Название берётся из title шага, код и исходная причина сохраняются. При выходе ошибки через if, for_each или call названия родительских шагов не дописываются. Для шага без title исходный текст не меняется. Формат применяется и к заданному в JSON message; результат доступен в error.message задания, журнале и callback.

В JSON 3.2.1 специальная проверка экрана «Компьютер не готов к работе» удалена. Вход использует обычное ожидание списка ЭЦП или завершения автоматической авторизации. Если условие не выполнено, возвращается технический тайм-аут; API 0.9.3 добавляет название исходного шага.


С JSON 3.4.0 описания ошибок проверки сохраняются в TXT-артефакт и в строковое поле Rezult_N.error_message соответствующего отчёта. Поле validation_result остаётся статусом панели, validation_protocol — ссылкой на TXT. В job.error.message перечисляются ведомство, исходный XML и описания ошибок; те же поля входят в callback. Структуры Rezult_N остаются плоскими. Старые результаты завершённых заданий автоматически не изменяются.

Стандартный protocol_selector выбирает всю панель validation_scope_selector, включая разделы и пояснения. Исполнитель JSON учитывает совпадение селектора с самой панелью, а не только с её потомками, и дожидается строк ошибок по validation_error_selector: заголовок отчёта, один заголовок со счётчиком и датой не считается протоколом ошибки. Если текст не появился до validation_timeout_ms, возвращается VALIDATION_PROTOCOL_NOT_READY. Для своего UI-профиля protocol_selector должен охватывать описания ошибок; селектор только шапки панели больше не подходит. Для этой доработки достаточно заменить весь script_text актуальным JSON; минимальный API остаётся 0.9.4.

validation_error_selector задаёт строки ошибок внутри панели; стандартное значение — [data-qa="journal_check_result"]. При своём UI-профиле укажите соответствующий селектор строк или null для проверки только текста протокола. Пустая строка ошибки не считается загруженной; служебный заголовок отчёта не заменяет описание ошибки.
