# Централизованное обновление Windows-УН

Для закрытого GitHub настройте [компьютер выпуска](../operator-guide/12-private-repository.md): только он получает исходники. Центр принимает подписанный пакет, а агенты скачивают его с центра по индивидуальным токенам; GitHub-ключи на УН не устанавливаются.

API **0.11.0**, протокол оркестратора и агента **1**. Проект содержит центральный сервис, панель, независимый агент, выпуск подписанных релизов и установщик. На существующие УН они автоматически не устанавливаются. Целевая ОС агента — Windows Server 2022, Node.js 24+, Windows PowerShell 5.1. Центральный сервис работает на Linux или Windows с Node.js 24+.

## Компоненты

| Файл | Назначение |
|---|---|
| `fleet/server.mjs` | Центральный HTTP-сервис, панель, SQLite-реестр УН, релизы и журнал |
| `fleet/agent.mjs` | Исходящий опрос центра, локальный журнал, управление обновлением |
| `windows/install-fleet-agent.ps1` | Первоначальная установка независимой задачи агента от SYSTEM |
| `docs/project-guide/tools/update-one-un.ps1` | Обновление одной УН с резервной копией и автоматическим откатом при неудачном запуске |
| `fleet/rollback-update.ps1` | Откат кода/зависимостей/задачи после неудачной проверки новой версии |
| `scripts/fleet-release.mjs` | Ключи подписи, сборка и публикация релиза |
| `scripts/fleet-enroll.mjs` | Массовая регистрация и выдача индивидуальных конфигураций |
| `ansible/install-fleet-agent.yml` | Первоначальная установка агентов по существующему WinRM inventory |

Агент живёт вне каталога API и не останавливается вместе с worker. В режиме broker API работает от SYSTEM; пользователь интерактивного worker, его браузер и ЭЦП при штатных последующих обновлениях сохраняются. Центральному сервису не передаются Windows-пароли, локальные API_KEY, XML и результаты заданий. Токены агентов отдельные, отзываемые; центральная БД хранит их хеши.

## Алгоритм

1. Администратор выбирает подписанный релиз, УН, окно времени, пилотную группу и размер партии. Сначала обновляются пилотные УН; остальные получают команды после успеха всех пилотов. Общий предел задаёт `FLEET_MAX_CONCURRENT`, предел одной раскатки — `batch_size`.
2. Агент проверяет подпись и минимальную совместимую версию API. Включает обслуживание с owner `fleet-<deployment_id>`: новые задания не принимаются, уже принятые queued/running/retrying завершаются.
3. Дожидается выполняющихся обработчиков, callback и скачиваний. Пока обслуживание активно, модуль питания получает блокировку `SERVICE_MAINTENANCE`. Его сохранённые настройки не меняются: после снятия обслуживания прежняя политика снова действует.
4. Скачивает пакет, проверяет SHA-256 и длину. Закрывает новые скачивания и изменения API, повторно проверяет освобождение УН. Запускает независимую копию локального обновлятора.
5. Обновлятор сохраняет код, действующие конфигурацию/данные, задачу и при необходимости зависимости. Останавливает подтверждённые задачи API и worker, устанавливает код и запускает обе задачи.
6. Проверяет точную версию, UN_ID, основные проверки `/health`. Затем выполняет фиксированный безопасный JSON-сценарий записи и чтения временного артефакта. Проверка не обращается к СБИС, ЭЦП, рабочим callback и реальным отчётам. Она проверяет исполнитель/файлы, а не каждый бизнес-сценарий.
7. При успехе снимает обслуживание, проверяет обычный `/health`, отправляет подтверждение. При неудачном запуске откатывает сам обновлятор; при сбое последующей проверки — агент. После подтверждения старой версии обслуживание снимается, результат `rolled_back` останавливает дальнейшую раскатку.

Обслуживание и журнал агента сохраняются на диске. Сетевые сообщения имеют идентификаторы и доставляются повторно без повторной установки. Если агент перезапустился во время установки, он читает локальный файл результата. Если исход неизвестен, он оставляет обслуживание и состояние `recovery_required`, не запускает второй установщик. Неопределённая операция удерживает слот параллельности до разбора.

Ожидание занятой УН ограничено `drain_timeout_seconds` (1800 по умолчанию). При превышении установка откладывается на минуту; после трёх попыток раскатка приостанавливается. Выдача новых команд прекращается по окончании окна. Уже начатая установка завершается и после паузы/окончания окна. При отсутствии heartbeat активного агента более `offline_timeout_seconds` (180 по умолчанию) новые назначения приостанавливаются. Выключенные УН получают команду после включения; агент не включает ВМ через гипервизор. Недоступные пилотные УН задерживают основную партию.

## Первое внедрение

Нужны центральный сервер, постоянный диск для SQLite/пакетов, DNS и HTTPS-сертификат. УН требуется исходящий HTTPS-доступ к нему. Новые входящие порты на УН не нужны. WinRM/административные права для первоначальной установки и включение ВМ обеспечивает инфраструктура.

**API 0.9.x не имеет режима обслуживания.** Один раз обновите пилотные УН до 0.11.0 по [ручной инструкции](04-update-one-un.md), затем установите агент. Первое обновление до 0.11.0 новым агентом выполнить нельзя: он возвращает `BOOTSTRAP_REQUIRED`. После пилота выполните первоначальное внедрение остальным УН административными средствами. Первый управляемый следующий релиз должен быть новее установленного, например 0.11.1.

### Ключ подписи релизов

На компьютере выпуска, из корня проекта:

```powershell
npm run fleet:release -- keygen --out C:/ScriptFactorySigning
```

`release-private.pem` храните только у выпускающего релизы, вне Git и центрального сервера. На оркестратор и УН передаётся только `release-public.pem`. Публичный ключ первоначально устанавливает администратор; команда обновления не может заменить его своим ключом. Ротация доверенного ключа — отдельная административная операция.

### Центральный сервис

Скопируйте `fleet/controller.env.example` в `fleet/controller.env`. Задайте случайный `FLEET_ADMIN_TOKEN` не короче 32 символов, публичный ключ и постоянный `FLEET_DATA_DIR`. Генерация токена и запуск:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
npm run fleet:start
```

По умолчанию сервис слушает `127.0.0.1:34001`, проверка — `/health`. Публикуйте через HTTPS reverse proxy; пример — `fleet/nginx.conf.example`. Панель открывается по корню адреса. Логин Basic — `admin`, пароль — `FLEET_ADMIN_TOKEN`. Административный HTTP API и CLI используют `Authorization: Bearer <FLEET_ADMIN_TOKEN>`. Ограничьте административный доступ корпоративной сетью/VPN на reverse proxy.

Для Linux есть `fleet/script-factory-fleet.service`: создайте системного пользователя `sf-fleet`, установите Node 24+, разместите проект в `/opt/script_factory`, окружение в `/etc/script-factory/fleet.env`, данные в `/var/lib/script-factory-fleet`. Подставьте эти пути в переменные, установите unit и запустите systemd. Конкретные учётные записи, DNS, сертификаты и резервное копирование сервера настраивают администраторы.

HTTP агент/CLI разрешают только на loopback для локальных тестов; остальные адреса требуют HTTPS. TLS не отключается. Для корпоративного УЦ обеспечьте доверие у Node от SYSTEM, не используйте `NODE_TLS_REJECT_UNAUTHORIZED=0`.

### Регистрация и установка агентов

Одну УН можно зарегистрировать через панель; ключ показывается один раз. `id` агента — до 100 латинских букв, цифр, `_`, `-`. `un_id` копируется без изменения из действующего `.env` УН, может содержать кириллицу; длина до 200 символов, без управляющих символов. Одна регистрация соответствует одному уникальному UN_ID. Группа также может иметь русское название.

Для массовой регистрации подготовьте JSON по `fleet/nodes.example.json` с индивидуальными путями и локальными портами:

```powershell
$env:FLEET_ADMIN_TOKEN = 'КЛЮЧ_АДМИНИСТРАТОРА'
npm run fleet:enroll -- --url https://fleet.example.org --inventory C:/Deploy/nodes.json --out C:/Deploy/enrollments
```

В защищённом каталоге появятся `<id>.json`, соответствующие `fleet/agent.config.example.json`. При частичной ошибке уже созданные регистрации сохраняются: исключите завершённые строки и повторите оставшиеся. Ключи не перегенерируются неявно; потерянный ключ можно явно перевыпустить в панели.

Передайте индивидуальный JSON, публичный ключ и исходники релиза на УН. В PowerShell администратора:

```powershell
& C:/script_factory/windows/install-fleet-agent.ps1 `
  -ConfigFile C:/Deploy/un-001.json `
  -ReleasePublicKey C:/Deploy/release-public.pem
```

Установщик создаёт `C:/ProgramData/ScriptFactoryAgent`, ограничивает доступ SYSTEM/Administrators, копирует агент/помощники, создаёт задачу `ScriptFactory-Fleet-Agent` от SYSTEM и запускает её. Запуск — при старте ОС и раз в минуту, если процесс остановлен; одновременно работает один экземпляр. Не размещайте агента внутри обновляемого проекта. После установки удалите исходную копию токена из `C:/Deploy`. В панели должны появиться контакт, версия API и готовность.

Агент не создаёт интерактивный сеанс robot и не настраивает автологин. После перезагрузки API/браузеру по-прежнему нужен правильный пользовательский сеанс.

Массовая первоначальная установка через `ansible/install-fleet-agent.yml` использует группу `script_factory_windows`. Для каждого host задайте `script_factory_fleet_url`, `script_factory_fleet_node_id`, `script_factory_un_id`, индивидуальный `script_factory_fleet_token` в Ansible Vault, путь к публичному ключу на контроллере `script_factory_fleet_public_key`, фактические `script_factory_project_path`, `script_factory_env_file`, `script_factory_port`, `script_factory_task_name`. Пример запуска из `ansible/`:

```bash
ansible-playbook -i inventories/test/hosts.yml install-fleet-agent.yml --ask-vault-pass --limit pilot
```

Подставьте существующие inventory и пилотную группу. Playbook ставит агента поверх уже обновлённого API; он не мигрирует автоматически историческую структуру releases/shared. Сам агент автоматически не заменяет собственный код каждым релизом API: для его редкого обновления дождитесь отсутствия активной операции и недоставленных сообщений, остановите только задачу агента и повторите установщик. Работающий установщик прерывать нельзя.

## Выпуск и раскатка

Поднимите версию, выполните тесты и зафиксируйте проверенный commit. Пакет берётся из commit, а не из незакоммиченной рабочей папки:

```powershell
npm run fleet:release -- build --ref КОММИТ_РЕЛИЗА --key C:/ScriptFactorySigning/release-private.pem --out C:/ScriptFactoryReleases
$env:FLEET_ADMIN_TOKEN = 'КЛЮЧ_АДМИНИСТРАТОРА'
npm run fleet:release -- publish --url https://fleet.example.org --manifest C:/ScriptFactoryReleases/ID.json --zip C:/ScriptFactoryReleases/ID.zip
```

В ZIP включаются только разрешённые каталоги кода и шаблоны: `.env`, секреты, work, outputs, данные, XML и node_modules не включаются. Пакет подписывается Ed25519 и проверяется центром и агентом. Опубликованный ID неизменяем: другой ZIP поверх него не устанавливается.

В панели выберите готовый релиз и УН. Первыми выберите 2–3 пилотные строки, задайте canary_count, окно и batch_size. На первых испытаниях batch_size=1, после приёмки — например 10. Пауза не обрывает текущую установку; «Отменить ожидающие» отменяет только ещё не выданные команды. После failed/rolled_back нажмите «Повторить», затем «Продолжить». Для просроченного окна отмените ожидающие команды и создайте новое окно.

Формат принимает только `database_schema=unchanged`. Это обязательство автора релиза: подпись сама по себе не доказывает совместимость БД. Миграции, удаление старых файлов, обновление Node/ОС/браузера требуют отдельной проверенной процедуры. Установка кода остаётся overlay; DATA_DIR автоматически не откатывается поверх данных. Если зависимости изменились, `npm ci` выполняется в staging: нужен доступ к npm registry/корпоративному зеркалу. Готовый офлайн-набор node_modules не поставляется.

## Доработка распределения в 1С

Исключать УН с `ready=false` из распределения заданий. При обслуживании `/health` возвращает HTTP 503 и `maintenance.active=true`. Новый POST jobs получает HTTP 503 с `error.code=SERVICE_MAINTENANCE`: направить задание на другую УН либо повторить позже с тем же uid. Уже принятые задания не отменяются. В draining повтор существующего uid может вернуть прежнее задание; в installing изменения закрыты полностью.

Запускать обновления из 1С необязательно — есть панель администратора. Ключ администратора оркестратора обычному клиенту 1С не передавать. Обновление API не заменяет `script_text`: JSON-сценарии распространяются и версионируются отдельно.

## Диагностика и восстановление

Состояния: queued, assigned, draining, downloading, installing, verifying, succeeded, rolled_back, failed, recovery_required. deferred означает ограниченную отсрочку; superseded — заменённую явным повтором попытку. После перезапуска центрального сервера состояния сохраняются.

- succeeded: точная версия, готовность и безопасный сценарий проверены, обслуживание снято.
- rolled_back: предыдущая версия подтверждена, обслуживание снято, раскатка приостановлена.
- recovery_required: исход неизвестен или откат не подтверждён. УН не получает вторую установку и удерживает слот параллельности до разбора. Не удаляйте журнал ради повторного запуска.

Журнал агента — `data/state.json`, результаты — `<deployment_id>.result.json` и `<deployment_id>.rollback.json`, подробный локальный протокол обновлятора — рядом с результатом, с окончанием `.log`. stdout/stderr агента сохраняются в `data/agent-out.log` и `data/agent-err.log`. Резервная копия содержит manifest.json, saved.env, task.xml, код, данные и при необходимости зависимости; каталог ограничивается SYSTEM/Administrators и остаётся на УН. Центральная SQLite хранит последние 10000 событий и историю установок; overview возвращает последние 200 событий. Настройте резервное копирование и контроль места. Автоматического удаления пакетов и резервных копий нет: администратор очищает их после приёмки, сохраняя нужный откат.

При неизвестном исходе сначала проверить, завершился ли установщик; второй не запускать. Проверить код, версию, задачу, зависимости и сеанс worker. После подтверждённого восстановления выполнить POST `/api/v2/system/maintenance/verify` с обычным X-API-Key и `{"owner":"fleet-ID_ОПЕРАЦИИ"}`, затем POST `/api/v2/system/maintenance/end` с тем же owner. Проверить обычный `/health`. Дождаться свежего heartbeat с `api_ready=true`, `maintenance=false`. Кнопка «Подтвердить восстановление» после этого разрешит дальнейшие действия; это подтверждение администратора, не объявление установки успешной. Ошибку можно явно повторить или отменить ожидающие УН и создать новую раскатку.

## Методы

Локальный API УН, обычный X-API-Key:

| Метод | Назначение |
|---|---|
| GET `/api/v2/system/maintenance` | active, owner, phase, blockers, ready_to_update |
| POST `/api/v2/system/maintenance/begin` | `{owner, reason?}`: закрыть приём и блокировать питание |
| POST `/api/v2/system/maintenance/seal` | `{owner}`: запретить скачивания и изменения после освобождения |
| POST `/api/v2/system/maintenance/verify` | `{owner}`: фиксированная безопасная проверка исполнителя/артефакта |
| POST `/api/v2/system/maintenance/end` | `{owner}`: снять обслуживание после восстановления |

Центральный API, административный Bearer:

| Метод | Назначение |
|---|---|
| GET `/health` | Доступность без авторизации |
| GET `/api/fleet` | Реестр, операции, релизы, журнал без ключей |
| POST `/api/nodes` | `{id, un_id, group?}`: регистрация с однократной выдачей token |
| POST `/api/nodes/{id}/revoke`, `/rotate` | Отозвать или явно заменить ключ |
| POST `/api/releases` | `{manifest, signature}`: регистрация подписанного релиза |
| PUT `/api/releases/{id}/package` | ZIP с Content-Type application/zip; SHA и длина проверяются |
| POST `/api/rollouts` | release_id, node_ids, canary_count, batch_size, start_at, end_at; необязательные drain_timeout_seconds, offline_timeout_seconds |
| POST `/api/rollouts/{id}/pause`, `/resume`, `/cancel` | Управление выдачей команд |
| POST `/api/deployments/{id}/retry` | Явный повтор failed/rolled_back с новым ID |
| POST `/api/deployments/{id}/resolve` | `{confirm_recovered:true}` после ручного восстановления и свежего heartbeat |

Исходящий протокол агента с индивидуальным Bearer: POST `/agent/{id}/heartbeat`, POST `/agent/{id}/reports/{deployment_id}`, GET `/agent/{id}/packages/{release_id}`. Скачивается только назначенный пакет; отчёт принимается только для своей УН. УН не принимает произвольных команд терминала из центра.

## Приёмка

Локальные тесты проверяют обслуживание реального API, сохранение блокировки, завершение очереди, скачивания, защиту от выключения, подпись/целостность ZIP, отзыв токена, пилотную группу, параллельность, паузу по ошибке, повторную доставку сообщений и цикл агента с имитацией Windows-установщика.

Это не заменяет Windows-пилот. До 300 УН выделите 2–3 Windows Server 2022: bootstrap 0.11.0, агент, следующий подписанный релиз. Проверить реальную замену файлов и откат задачи, смену зависимостей, занятую очередь/callback, потерю связи, перезапуск агента/Windows, права SYSTEM, интерактивный worker и возобновление политики питания. Затем увеличивать партии. Реальные отправки отчётности не использовать как автоматический smoke-тест.

Для API 0.11.0 учитывайте [разделение API и интерактивного worker](12-api-worker-startup.md): API запускается при старте Windows, готовность исполнения проверяется отдельно через `/health`. Для первоначального внедрения и проверки обновления нужен вошедший пользователь worker.

В API 0.13.0 добавлены [профили конфигураций, секреты, адреса УН и массовое применение](../operator-guide/09-orchestrator-configurations.md). Для доставки конфигураций требуется обновление независимого агента до версии 2.
