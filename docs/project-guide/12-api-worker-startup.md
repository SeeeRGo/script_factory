# API при включении УН и интерактивный worker

В API 0.11.0 добавлен режим `EXECUTION_MODE=broker`. HTTP API запускается под SYSTEM при старте Windows; сценарии исполняет отдельный процесс в сеансе настроенного пользователя (по умолчанию `COMPUTERNAME\robot`). Это две задачи Планировщика, а не служба SCM. Для Windows Server 2022 требуется пилотная проверка; установка на рабочие УН автоматически не выполняется.

## Установка и обновление

Node.js 24+ должен быть установлен для всей машины. Подготовьте `.env`, локального пользователя robot, браузер и компоненты ЭЦП по [инструкции установки](03-install-windows.md). Для новой установки выполните из повышенной Windows PowerShell 5.1:

```powershell
cd C:\script_factory
.\windows\install-task.ps1 -ProjectPath C:\script_factory -Port 33001
.\windows\install-saby-task.ps1 -ProjectPath C:\script_factory
```

Порт должен совпадать с `PORT` в `.env`; при другом порте подставьте его. Для другой учётной записи добавьте `-RunAsUser "$env:COMPUTERNAME\robot2"`. Установщик создаёт токен локального канала, записывает `EXECUTION_MODE=broker`, `WORKER_ACCOUNT`, `WORKER_PORT` и `WORKER_TASK_NAME`. Токен не передают в 1С и не публикуют. Канал слушает только 127.0.0.1; открывать его в Firewall или пробрасывать наружу не нужно.

Для существующей установки используйте [помощник обновления](04-update-one-un.md): он останавливает обе задачи, сохраняет конфигурацию и XML задач, выполняет переход и проверяет готовность. Перед обновлением пользователь worker должен войти в Windows. Не запускайте установщик поверх работающего API; он откажется при занятом HTTP-порте. Перед миграцией проверьте, что прежний worker — обычный пользователь, а не SYSTEM. Если задачи назывались иначе, передайте правильные имена; для Saby можно явно задать `-WorkerTaskName` и `-TaskPath`.

Задачи по умолчанию:

| Задача | Учётная запись | Запуск |
| --- | --- | --- |
| ScriptFactory-Test-UN | SYSTEM | При включении Windows |
| ScriptFactory-Test-UN-Worker | robot | После входа пользователя |
| ScriptFactory-Saby | тот же robot | После входа пользователя |

API и worker контролируются скрытыми PowerShell-процессами: после завершения Node предусмотрен повторный запуск через 10 секунд. Планировщик также повторяет попытку запуска раз в минуту. Во время обновления задачи отключаются, чтобы повторный триггер не запустил старый процесс среди копирования файлов. Обновлятор и откат восстанавливают обе задачи. Saby устанавливается отдельным скриптом; изменение пользователя worker требует повторной настройки задачи Saby под того же пользователя.

## Вход пользователя и Saby

Новая архитектура запускает API без входа robot, но не создаёт интерактивный рабочий стол автоматически. Для выполнения сценариев после перезагрузки без RDP администратор должен настроить автоматический вход robot, например [Microsoft Sysinternals Autologon](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), с учётом политики организации. Установщик проекта этого не делает и не хранит пароль для входа в Git. Проверьте лицензию, подписи, Saby и браузер именно под robot; настройка под другим администратором не переносит пользовательские сертификаты.

Разрыв RDP, блокировка экрана и выход из Windows различаются. Видимую автоматизацию Яндекса необходимо проверить после перезагрузки без RDP именно в целевой конфигурации: наличие процесса worker само по себе не гарантирует работу диалогов ЭЦП. `/health` подтверждает доступность браузера, базы и исполнителя, но не лицензию СБИС и не доступность каждой ЭЦП.

## Диагностика и поведение 1С

Локальные адреса при `PORT=33001`:

* `http://127.0.0.1:33001/live` — HTTP 200 означает, что API отвечает; вход robot не требуется. Алиас — `/api/v2/live`.
* `http://127.0.0.1:33001/health` — HTTP 200 и `ready=true` означают готовность принимать задания. HTTP 503 содержит причину. Оба метода доступны без API-ключа.
* `GET /api/v2/system/worker/status` с `X-API-Key` — пользователь, session_id, PID и состояние worker. В старом режиме `inline` сведения об отдельном процессе отсутствуют.

Внешний адрес зависит от проброса портов. По умолчанию используется HTTP; HTTPS требует отдельно настроенного TLS-прокси.

| Ответ | Что делать в 1С |
| --- | --- |
| TCP-ошибка или тайм-аут | Повторять только в пределах общего срока ожидания включения УН; отсутствие ответа не отличает выключенную ВМ от сетевой неисправности |
| HTTP 401 | Проверить API-ключ; ожидание входа Windows не исправит авторизацию HTTP |
| HTTP 503, `error.retryable=true` | Повторить проверку через `Retry-After` (обычно 2 секунды), соблюдая общий срок |
| HTTP 503, `error.retryable=false` | Показать диагностику, не ждать бесконечно |
| HTTP 200, `ready=true` | Можно ставить задание |

`worker.state` принимает `WAITING_FOR_SESSION` (нет нужного сеанса Windows), `WORKER_STARTING` (ожидание процесса), `WORKER_SESSION_REQUIRED` (истёк срок ожидания входа), `WORKER_START_FAILED` (процесс/браузер не готов), `WORKER_TRANSPORT_FAILED` (локальный порт недоступен), `WORKER_UNRESPONSIVE` (не подтверждена остановка прежней работы) или `READY`. При POST задания до готовности возвращается HTTP 503 `WORKER_UNAVAILABLE` с подробностями worker; новое задание не создаётся. Для неизвестного результата POST при сетевом обрыве используйте один и тот же `uid`, чтобы не создать дубликат.

Срок ожидания worker — `WORKER_STARTUP_MS=120000`. Он ограничивает рекомендацию ждать, а не запрещает позднее подключение: после входа пользователя worker может стать готовым. На Windows наличие сеанса проверяется в фоне, а не внутри каждого HTTP-запроса. При старте до первой проверки возможно общее состояние `WORKER_STARTING`.

## Настройки, журналы и восстановление

| Параметр | Назначение и значение по умолчанию |
| --- | --- |
| EXECUTION_MODE | `inline` сохраняет прежний совместный процесс; Windows-установщик выбирает `broker` |
| WORKER_ACCOUNT | Полное имя пользователя Windows, задаётся установщиком |
| WORKER_AUTH_TOKEN | Секрет локального канала, от 32 символов, задаётся установщиком |
| WORKER_PORT | Локальный порт; по умолчанию PORT+1 |
| WORKER_TASK_NAME | Имя пользовательской задачи, задаётся установщиком |
| WORKER_STARTUP_MS | 120000; срок ожидания входа/запуска |
| WORKER_HEARTBEAT_MS / WORKER_LOST_MS | 3000 / 15000; период heartbeat и обнаружение потери связи |
| WORKER_CANCEL_MS | 10000; ожидание подтверждения остановки |
| WORKER_MAX_MESSAGE_BYTES | 16777216; предел одного сообщения локального канала |
| WORKER_MAX_PARALLEL_JOBS | 100; потолок worker, фактический параллелизм также ограничен max_parallel_jobs API |

Параметры меняются в `.env`; перезапустите обе задачи в согласованное время при пустой очереди. Секрет и пути должны совпадать у обоих процессов. Не выводите `.env` целиком в протокол диагностики. Установщик выдаёт SYSTEM/администраторам полный доступ к конфигурации и robot — чтение; robot также имеет доступ к данным результатов.

В `DATA_DIR/api-logs` — журналы запуска API, в `DATA_DIR/worker-logs` — пользовательского worker; `supervisor.log` показывает перезапуски. В `DATA_DIR/worker-state` хранятся служебные журналы неподтверждённых выполнений; они могут содержать результаты и деловые данные, не публикуйте их. Не удаляйте их во время выполнения.

Принятое задание сохраняется до HTTP 201. Очередь переживает перезапуск API. Если API или worker потеряны во время исполнения, исход уже выполненных действий может быть неизвестен: задание получает `WORKER_EXECUTION_UNCERTAIN` и не отправляется автоматически повторно даже при настроенном retry. Проверьте кабинет СБИС/артефакты перед ручным повтором. Если остановка прежней работы не подтверждена, обновление и выключение блокируются до восстановления связи с worker. Полученный результат подтверждается worker только после сохранения в API.

Для модуля выключения исключаемый пользователь по умолчанию — `WORKER_ACCOUNT`, а не SYSTEM. Явные настройки `POWER_EXCLUDED_USER` и сохранённое переопределение API имеют приоритет. Во время начального ожидания worker автоматическое выключение блокируется; после истечения срока применяется обычная политика питания. Для первого пилота отключите фоновое выключение, чтобы оно не мешало диагностике загрузки.

## Обязательный Windows-пилот

На 2–3 тестовых Windows Server 2022 проверить: включение без RDP → `/live`; отсутствие robot → осмысленный `/health` 503; вход/автовход → `/health` 200; безопасное браузерное задание; Saby в том же сеансе; закрытие RDP; рестарт Node и Windows; обновление и откат обеих задач. Затем проверять массовую раскатку по [инструкции оркестратора](11-fleet-updates.md). Локальные Linux-тесты двух процессов не заменяют проверку Планировщика, прав и интерактивного браузера на Windows.
