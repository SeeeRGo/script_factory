# СБИС: полный сценарий из JSON

Актуальный файл: [sbis-report-full.json](sbis-report-full.json). Формат — `json-workflow`, версия сценария 2.0.2, минимальная версия системы 0.6.19. [sbis-report-full.request.json](sbis-report-full.request.json) содержит пример полного API-запроса.

Выбор ЭЦП и ведомства, сверка ИНН, выбор XML, проверки карточки, запуск проверки, сохранение текста результата, условия отправки и архивирования описаны в JSON. Сервер не содержит обработчика `select_authority` или специального исполнителя СБИС. Подпрограммы `browser`, `identity`, `validate`, `store_report`, `result` — массивы обычных шагов внутри `routines` этого файла.

Описание универсального формата и операций: [json-workflow.md](json-workflow.md).

## Индивидуальные параметры

| Параметр | Значение |
| --- | --- |
| `mode` | `preflight` — вход, выбор ведомств и сверка организации без импорта; `validate_only` — импорт и проверка без отправки; `send` — допускает отправку при дополнительных подтверждениях. |
| `browser_ignore_default_args` | Boolean, по умолчанию true: минимальный запуск для совместимости с Яндексом 24. Настройки браузера в `.env` не меняются; false возвращает стандартные аргументы Puppeteer. Поддержка — с API 0.6.19. |
| `submit_enabled` | Отдельный выключатель отправки. Требуются одновременно `mode=send`, `submit_enabled=true`, успешная проверка всех файлов ведомства и полностью заполненные шаги отправки. По умолчанию false. |
| `inn` | Полный ИНН выбранной организации: 10 или 12 цифр. |
| `certificate_inn` | ИНН владельца нужной ЭЦП; при null используется `inn`. |
| `certificate_selection_required` | true запрещает автоматический вход без явного подтверждения выбранной ЭЦП. |
| `skip_security_setup` | Разрешает пропуск необязательного создания логина/пароля СБИС. Первичная регистрация организации не выполняется автоматически. |
| `authority_prefixes` | Массив объектов `{authority, prefixes, ui?}`. Ведомства: FNS, SFR, ROSSTAT. Для всех трёх — три объекта. `ui` объекта переопределяет общие привязки для этого ведомства. |
| `authority`, `prefixes` | Одиночное ведомство и префиксы; используются только при `authority_prefixes=null`. |
| `allow_multiple` | Разрешает несколько выбранных самостоятельных отчётов одного ведомства. Выбирается последний файл для каждого префикса. Это не разрешение на загрузку связанных XML как отдельных отчётов. |
| `root_dir` | Каталог исходных XML на УН. Должен входить в разрешённые файловые корни. |
| `loaded_dir` | Существующий каталог архивирования подтверждённых отправок; также входит в разрешённые корни. |
| `upload_directory_steps` | Необязательное переопределение шагов Recorder перехода в каталог перед выбором XML. При пустом массиве JSON строит переход по `root_dir` на диске C. Для другого диска или другого устройства диалога задайте эти шаги явно. |
| `login_url`, `report_url`, `authenticated_url` | Адреса входа, отчётности и подтверждённого кабинета. |
| `validation_timeout_ms`, `submit_timeout_ms` | Время ожидания результатов проверки/отправки в миллисекундах; от 1 до 900000, дополнительно ограничивается тайм-аутом задания. |
| `ui` | Адреса разделов, селекторы, стандартные браузерные шаги и выражение ключа карточки. Эти настройки находятся в JSON. |

Перед любым импортом JSON проверяет наличие обязательных UI-привязок всех выбранных ведомств, выбирает файлы всех ведомств и запрещает выбор одного файла для двух ведомств. Затем создаёт общую сессию браузера. Каждый переход сопровождается повторной сверкой полного ИНН организации.

Шаблонный `ui.upload_steps` сначала открывает «Загрузить → С компьютера → Загрузки», затем содержит два завершающих шага: ожидание выбранной строки и двойной клик. JSON использует явный `upload_directory_steps` либо строит шаги по компонентам `root_dir` на диске C, затем проверяет точное имя и полный путь XML перед двойным кликом. Другое устройство файлового диалога требует изменения этих JSON-шагов.

После импорта проверяется единственная карточка, полный ИНН и её ключ. Сверка ИНН учитывает текст карточки и значения видимых input/textarea: в форме РСВ ИНН находится в поле ввода. Если реквизиты скрыты, они раскрываются обычным кликом мыши; уже раскрытые реквизиты повторно не сворачиваются. Исходное имя XML может отсутствовать на карточке, поэтому подтверждение опирается на имя/путь в диалоге и стабильный ключ открытого отчёта. Другой ключ при последующей проверке блокирует продолжение. Один ключ для разных XML возвращает `REPORT_BUNDLE_REQUIRED`: обработка связанных частей одного отчёта отдельными отправками запрещена.

Привязка кнопки «Проверить» и зелёной/розовой панели подтверждена для РСВ ФНС и ЕФС-1 СФР. Проверка требует единственного точного статуса и непустого текста панели проверки. Текст сохраняется в артефакт на УН; это текст интерфейса проверки, а не подтверждение получения официального протокола ведомства.

Отправка повторно открывает нужную карточку и повторно проверяет её. Перед нажатием записывается `submission_unknown`. Подтверждённый статус задаётся в `ui.sent_status_text`, область — в `ui.sent_scope_selector` или области карточки. После `submit_steps` JSON повторно сверяет полный ИНН и прежний ключ карточки. `ui.current_card_scope_selector` задаёт полную карточку вместе с её статусом; она обязательна для send. Явное окно отсутствия лицензии и единственный статус неотправленного отчёта в этой карточке возвращают `REPORTING_LICENSE_REQUIRED` / `license_required`, без покупки, повтора и архивирования. При противоречащем статусе либо другой карточке остаётся неопределённость. При неопределённом исходе результат `requires_reconciliation`; автоматического повтора задания нет. Архивирование разрешается только после подтверждения отправки всех файлов ведомства. Контрольные суммы проверяются повторно; существующие архивные файлы не перезаписываются.

## Передача из 1С

В `script_text` передаётся весь текст [sbis-report-full.json](sbis-report-full.json), включая `context`, `routines`, `steps`, `on_error`, `output`. Индивидуальные параметры можно передавать в отдельном `context` запроса. Альтернатива — поле `script` как объект JSON.

Пример запроса ограничен ФНС и содержит профиль зелёной/розовой панели проверки: ошибки НДС и успешная проверка РСВ проверены на УН. Для трёх ведомств передайте все три элемента `authority_prefixes` с подходящими префиксами и проверенными `ui` каждого ведомства. Значения null и пустые обязательные массивы в UI — незавершённые привязки; рабочий режим с ними остановится до запуска браузера. В `preflight` проверяются вход и организация, без импорта.

Сценарий также сохраняет JSON этого объекта в `result-N.json` в каталоге артефактов задания. Если финализация вызывается повторно из `on_error`, создаётся следующий номер; для загрузки выбирайте последний такой артефакт по `job.result.artifacts[].api_url`.

В ответе сохраняется структура `Rezult_1`: `state`, `inn`, `authority`, `mode`, `authorities`, `reports`, `phases`. У отчёта возвращаются `file_name`, `sha256`, `state`, `load_datetime`, `validation_result`, `file_selection_verified`, `report_key_verified`, ссылка `validation_protocol`, `sbis_status`, `archived_path`. Внутренний ключ карточки и сырой текст проверки в этот объект не включаются; текст доступен отдельным артефактом.

## Проверки и ограничения

Предыдущий специальный исполнитель 0.6.13 подтвердил на тестовой УН полный цикл ФНС до сохранения панели ошибок: `job_53762444-b254-46c7-a1f1-82a464182917`, 12/12 шагов, `validation_failed`, без отправки и архивирования. Это историческая проверка; сама по себе она не подтверждает новую реализацию 0.6.14.

После переноса JSON проверяется отдельно на локальных браузерных формах и тестовой УН. Локальные формы покрывают другой универсальный сценарий, обход трёх ведомств, выбор ЭЦП, неверный ИНН, точный файл/путь, ключ карточки, повторный импорт, несколько самостоятельных XML, повторную проверку перед отправкой, неопределённую отправку и архивирование.

Остаются ограничения реального кабинета: нет подтверждённой успешной проверки корректного комплекта НДС, совместной загрузки его связанных разделов, импорта и проверки настоящего XML Росстата, реального подписания и отправки. Для второго сертификата кабинет требует ручной первичной регистрации; она не выполнялась. Для отладки используются отдельные копии файлов: первоначально тестовая декларация, затем подготовленные бухгалтером РСВ и ЕФС-1. Исходные XML не изменяются; реальные подпись и отправка этих двух отчётов заблокированы лицензией.


Подтверждение новой реализации на УН: `job_b475fd0b-5b6e-4d45-a71b-326c70a4336e`, **108/108** фактически исполненных универсальных шагов, `preflight_completed`. ФНС, СФР и Росстат пройдены в одной сессии, полный ИНН подтверждён для каждого ведомства. Локально прошли **111/111** тестов проекта; на Windows/Yandex — **25/25** профильных тестов нового исполнителя и JSON СБИС.


Реальная проверка нового JSON через `script_text`: `job_eea694ba-5719-4e16-808a-cf3bd10c4c91`, `validation_failed` / `VALIDATION_ERROR`. Подтверждены исходный файл, полный ИНН и ключ карточки; текст проверки сохранён на УН (`protocol_saved=true`). `sent=false`, `archived=false`. В истории 147 универсальных шагов: 145 завершены успешно; два отмечены failed — явный `fail(VALIDATION_ERROR)` и содержащая его ветка `if`. Это намеренный возврат ошибок неполной тестовой декларации, а не сбой импорта или UI. XML не скачивались в локальный проект; исходные сданные отчёты не изменялись.

В версии сценария 2.0.1 после каждого перехода на страницу ведомства JSON дополнительно сравнивает origin и pathname с authority_url. Перенаправление в другой раздел блокируется с AUTHORITY_NOT_VERIFIED до импорта; reports_section_verified формируется из этой проверки.

Финальная проверка версии 0.6.15 и сценария 2.0.1: `job_e4d88029-eb45-479d-951a-28ca7a3bbd11`, **114/114** шагов, `preflight_completed`. Для всех трёх ведомств подтверждены ИНН и фактический origin/pathname. Итоговый локальный набор — **112/112** тестов, включая остановку при перенаправлении в другое ведомство до импорта.

На Windows/Yandex окончательный набор версии 0.6.15 прошёл **26/26** тестов универсального исполнителя и JSON СБИС, включая перенаправление в чужое ведомство.

12.10.2026: в сценарии 2.0.2 добавлены минимальный запуск Яндекса через универсальный параметр JSON и сохраняемый JSON результата. На дополнительной УН основной API обновлён до 0.6.19; запуск, вход по ЭЦП и preflight ФНС/СФР с полным ИНН подтверждены. Новая привязка поддерживает ссылку организации в профиле ИП; известная подсказка закрывается доверенным кликом мыши. РСВ ФНС импортирован, подтверждены имя/путь XML, полный ИНН из видимого поля и ключ карточки. Успешный статус «Ошибки не найдены» распознан JSON, текст проверки сохранён на УН. Переход к отправке заблокирован отсутствием лицензии «Отчетность»; подпись, отправка и покупка лицензии не выполнялись. ЕФС-1 СФР также импортирован и успешно проверен с полным ИНН и ключом карточки; текст проверки сохранён на УН. Его отправка блокирована тем же лицензионным окном. Полный локальный набор до обработки лицензии — 118/118; отдельные проверки лицензии, чужой карточки и отправки после этого изменения — 5/5.
